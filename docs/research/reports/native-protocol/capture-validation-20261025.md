# 20261025-014922 被动采集的离线核对结果

本文核对远程 `main` 的既有抓包，验证业务帧、XTEA、ENet 与节点发现；不运行客户端、不连接对端，不把心跳或传输 ACK 当成业务消息送达。

## 1. 结论

**这份抓包验证了静态规格中的业务帧头、固定 XTEA 密钥、未加密尾部、ENet reliable channel 0 和 1016 心跳。Go PoC 可以将原客户端心跳逐字节解码、重新编码。** 也观察到本机与两个局域网节点直接通信，以及 UDP 9011 的发现广播/响应。

**没有捕获启动握手、账户认证、1004 或 3011。** 因此还不能实现或宣称独立进程登录/发送完成，也没有 `recipient_observed`。

另一个重要修正：采集说明把外网 TCP 流称为“持续心跳”，但该流的 **12 个包均为零应用载荷 ACK**。它们呈 TCP 保活探测/应答样式，不是已经确认的内网通应用层心跳或服务器认证。

## 3. 五个原客户端心跳：帧头、加密与尾部均吻合

### 3.1 逐帧结果

| 原始帧号 | 方向 | ENet channel | reliable sequence | 应用总长 | 命令号 | 匹配的 ENet ACK 帧号 |
|---:|---|---:|---:|---:|---:|---:|
| 1 | P1 → C0 | 0 | 219 | 34 | 1016 | 2 |
| 23 | C0 → P1 | 0 | 231 | 34 | 1016 | 26 |
| 24 | C0 → P2 | 0 | 221 | 34 | 1016 | 25 |
| 27 | P2 → C0 | 0 | 219 | 34 | 1016 | 28 |
| 29 | P1 → C0 | 0 | 220 | 34 | 1016 | 30 |

五个 ENet SEND_RELIABLE 携带的应用帧完全相同：

```text
00000022 000003f8
 d529c5439de045c9 d3dc11866769e1fe dfa896e8e704a553 2f3e
```

字段解释：

- `00000022`：大端 34，包含 8 字节应用头。
- `000003f8`：大端 1016，是命令号，不是序列号。
- payload 长 26 字节，前 24 字节分成三个 XTEA 分组；最后 `2f3e` 即 `/>`，保持明文。
- 用样本内固定密钥 `8asfhj@k7*20hbla` 解密，五帧均得到精确的 26 字节正文：

```xml
<X_HEARTBEAT docver="1" />
```

用 Go `Encode(1016, payload)` 重新编码，与每个原始应用帧 **34/34 字节一致**。这不再只是自身往返测试：被比较的字节来自另一台主机采集的原客户端流量。

新增回归用例：`internal/nativeproto/frame_test.go` 的 `TestCapturedHeartbeatFrame`。fixture 只含无身份信息的应用心跳帧，不含 IP、用户资料或 ENet 连接编号。

### 3.2 心跳时间

同一对端 P1 发给 C0 的帧 1 与帧 29 相隔 **60.0304378 秒**，与静态发现的 60 秒应用心跳检查一致。

这是一个已观察到的间隔，不是对所有节点定时精度的证明；90 秒主采集没有连接断开过程，不能用它验证 120 秒超时或完整重连规则。

## 4. ENet 与直接通信

22 个 UDP 9012 datagram 全部可按本次出现的 ENet 命令完整拆解，无未解释尾字节：

| ENet 命令 | 数量 | 含义 |
|---|---:|---|
| 1 ACKNOWLEDGE | 11 | 传输层确认 |
| 5 PING | 6 | ENet 自身保活，不含 XML 应用帧 |
| 6 SEND_RELIABLE | 5 | 可靠发送，channel 0，承载上述 1016 |

带 sent-time 的这些包使用 4 字节 ENet packet header；SEND_RELIABLE command header 为 6 字节，随后是 34 字节应用帧，因此本次此类 UDP payload 总长为 **44 字节**。

11 个要求确认的命令均可按“反向端点、channel、reliable sequence、回显 sent-time”匹配到后续 ACK。五个应用心跳的 ACK 延迟约为 11.404、79.996、54.607、46.330、95.960 ms。

由此实际确认：

1. 同一客户端同时与两个局域网 IP:9012 双向通信，不是本窗口中只与单个中央服务器交换原生业务心跳。
2. 应用头无 sequence；可靠序列位于 ENet 外层。不同端点、不同方向的序号不能相互混用。
3. ENet PING 与应用层 1016 是不同层次；前者不能被误识别为加密正文。
4. ACK 只能证明传输层确认。这里没有聊天业务，不能记录 `recipient_observed`。

本次没有 ENet CONNECT/VERIFY_CONNECT、分片或压缩包。当前小型离线解析没有因此变成完整 ENet 实现，也不能证明客户端从不使用这些功能。

## 5. UDP 发现广播与响应

| 原始帧号 | 流向 | UDP payload 长度 | 三个大端头字段 |
|---:|---|---:|---|
| 11 | P2 → 本地子网广播地址 | 304 | `(304, 1, 1)` |
| 12 | P2 → 全局广播地址 | 304 | `(304, 1, 1)` |
| 13 | C0 → P2 单播 | 304 | `(304, 2, 1)` |
| 14 | C0 → P2 单播 | 304 | `(304, 2, 1)` |

这与静态 `0x659050` 的 `0x130` 长度、调用方指定类型、版本 1 一致。类型 1 是本次观察到的发现广播，类型 2 是紧随其后的单播响应；不是命令 1000，也不是服务器认证响应。

四包在 `0x18..0x1d` 的原始六字节均为 `23 33 23 34 23 34`，可按三个大端 16 位值读作 9011、9012、9012。这里只核对原始值，不在缺少完整字段契约时将所有端口强行命名。

发现包还包含身份/节点资料，本报告不复制这些字段。**304 字节发现包与“8 字节头 + 加密 XML”的业务帧是两种不同格式**，不能送进同一个解码器尝试。

## 6. 外网 TCP 流不能证明服务器认证

原始帧 3、4、5、6、19、20、21、22、31、32、33、34：

- 均为 TCP ACK，应用载荷为 0。
- 远端重复相同 sequence，采集端反向返回相同确认号；呈现 TCP 保活探测/应答样式。
- 没有 SYN/FIN/RST，也没有 HTTP、XML、账号认证或其他应用字节。
- 采集前后对应 socket 状态为 `CloseWait`，它不是本窗口中新建立的登录连接。

因此可以否定“这 12 帧已经展示服务器应用心跳/认证”的说法；**不能反向推断该公网端点永远无关、应用绝无服务端，或本次已得到中央登录协议。**

## 7. 本次证明了什么，还缺什么

| 问题 | 本次结果 |
|---|---|
| 业务帧长度和字节序 | 实际验证：34 字节；长度包含应用头；命令 1016 大端 |
| 固定 XTEA 密钥及分组规则 | 实际验证：三个加密分组和末尾两字节明文；Go 重新编码完全一致 |
| ENet reliable、channel 与序列 | 实际验证：channel 0；序列在 ENet 外层；全部相关 ACK 可匹配 |
| P2P 通信 | 实际观察到 C0 与两个局域网节点直接交换 ENet 应用心跳 |
| UDP 发现格式 | 实际验证 304 字节及类型 1/2、版本 1 |
| 60 秒应用心跳 | 观察到同向间隔 60.0304378 秒，符合静态调度 |
| 120 秒超时、断线与重连 | 无断开事件，未验证 |
| 1000 握手及身份初始化 | 无启动过程、无 1000，未验证 |
| 账户凭据/服务器认证 | 无对应应用字节，未恢复 |
| 1004/3011 的完整业务语义与送达 | 未采集、未发送、未验证 |

过滤器是端口过滤，不是逐包 PID 标记。采集前后端点相同，有助于解释包归属，但不能证明窗口内从未出现过又消失的临时端口；不把这次过滤范围外的流量描述为不存在。
