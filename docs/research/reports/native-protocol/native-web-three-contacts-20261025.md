# Web 三客户端联系人发现修复与验证

## 结论

2026-10-25，Web 后台从原有单对端扩展为显式子网发现与共享 Host 多对端。修复原厂发现包公告 IP 为 `0.0.0.0` 时被错误拒绝的问题后，真实只读 HTTP 检查得到：**3 个联系人、3 个在线、3 个不同连接完成双向 READY**。

该结果是程序的协议状态和 HTTP 列表观察，不冒充用户已经核对 Windows UI 或网页，不表示聊天送达。本轮开发与三次发现验证未由助手提交聊天请求；三个发现会话的发送阶段计数均为0。此前由网页操作者产生的发送记录单独保留，不归入本次验证。

## 原因与修复

1. 原 Web 只构造一个 `Client`，发现入口丢弃 `RemoteDiscovery` 以外的来源，列表最多学习一个当前对端。这不是前端筛选或刷新错误。
2. 新增 `Host`，在同一个独立身份和一组发现/ENet真实 socket 下分派多个连接；各自维护 ENet、应用 READY、心跳及正常退出。每个身份单独报告在线，不以唯一 `PeerUserID` 判断所有联系人。
3. 最初 Host 要求公告 IP 等于 UDP 来源。真实响应的该字段均为 `0.0.0.0`，所以三份正常响应全部被拒绝。诊断版本保留具体拒绝字段后确认了这一点，没有通过盲目放开所有校验来猜测。
4. 现在允许零公告 IP，但连接目标仍取受显式子网约束的 UDP 实际来源；非零公告地址不符仍拒绝，发现端口、类型、FEATURE、身份与会话检查保持。原始节点包不改写。
5. 联系人持久化改为串行合并和逐份新快照，避免后一个连接覆盖前一个联系人；旧快照及失败记录保留。

## 真实尝试与授权

用户先批准开发后，在指定子网做一次标准广播发现和最长10分钟上线验证，不扫描、不发聊天。第一次未成功后停止并保留记录；用户随后另行批准最多两次诊断，每次最多3分钟。每次仅一个标准定向广播，不枚举地址，不因失败自动重启。

| 尝试 | 开始 UTC | 结果 |
|---|---|---|
| 初次共享 Host | 18:43:10 | 三份响应被拒绝，无就绪对端；162.054秒后人工正常停止 |
| 诊断1 | 18:50:40 | 明确记录三份响应的公告 IP 为0，实际来源为子网内三台客户端；170.002秒到期正常停止 |
| 诊断2／修复复验 | 18:54:35 | 3个联系人全部在线，3个不同连接发出 `peer_ready`；170.209秒后正常下线，`graceful_exit=true`、`chat_sends=0` |

真实身份、对端、群资料、访问密码和原始日志保持私有，不写入本文。沿用现有 Web 独立身份，未读取 Windows 客户端数据库、内存、聊天历史或凭据。

只读观察以独占创建方式保存为：

```text
local/nativeclient/web-preview/host-three-contacts-observation-20261025.json
```

该观察来源为 `authenticated_readonly_http`，保存当时状态；`recipient_ui_observation` 仍为 `unknown`。逐次 `session-*.jsonl`、联系人快照及失败记录均保留，没有覆盖成成功。

## 回归测试

- 三个真实 Go `Client` 在同一 Host 双 socket 下上线，三个联系人递增合并；逐目标单聊不串人，单个对端退出不影响其他对端，Host正常退出全部连接。
- 三个独立合成接收端分别解析完整正文；这部分是合成发送测试，不属于真实发送授权。
- 原厂零公告 IP 用例先失败，再通过；非零错误公告地址、未知类型、端口错误、FEATURE不符继续拒绝。
- Web回归验证三个实际就绪身份均显示在线、可单独选择；一个离线只更新其自身。
- 检查广播只发生一次、目录/观察回调失败停止 Host、单对端失败隔离、群旧成员版本失效、总会话时限及关闭。

## 保留范围

- 原 `Client` 和 stdin 命令仍是显式单对端；Web需要 `-discover` 才启用本子网标准发现。
- `Host` 就绪不等于已有在线客户端；只有各身份双向 READY 才计为在线联系人。
- 多成员群投递尚未实现；仍仅支持完整成员为本机与一个已连接成员的群，按该成员路由。
- 不支持自动重连、扫描或自动补发聊天。入群仍由操作者人工处理。
- 本次上线授权不延续为后续真实发现、连接或聊天授权。运行方式见 [nwtweb](../../../tools/nwtweb.md)。
