# 独立 Linux Go 节点真实上线验收

本文记录当前 Linux 主机作为全新内网通节点，与指定 Windows 原客户端进行的已授权单播上线验证。协议就绪、原客户端 UI 观察和正常退出分别记录；未发送聊天消息。

## 1. 验收结论

**独立 Go 客户端上线验收通过。** 本机 `10.1.1.30`、节点名称 `NWT-Go-Linux`，与指定对端 `10.1.1.241` 完成节点控制、双向 1000/1018、应用心跳及正常退出；用户明确回复 **“已看到在线”**，确认原客户端列表显示该新节点在线。

这不是把 ENet ACK 或离线回放当作上线成功。此次验收包含独立原客户端的实际观察。

范围是**单对端上线**；没有完成独立网络的 1004/3011 聊天发送、HTTP 集成、多 peer 共享 host、原生群业务或异常重连验收。原 IPC 网关保持不变。

## 2. 身份与操作范围

- 使用 Go 自己生成并持久保存的新 UserID，四次尝试保持同一身份；没有读取、复制或修改 Windows 客户端的 acc/凭据。
- 每次使用独立的新会话 GUID 和传输 ConnectID，按完整会话字段比较选择主动或被动角色。
- 仅向已明确指定的 `10.1.1.241` 单播发现、建连与控制消息；每次最长90秒，不扫描或广播。
- 不修改或重启 Windows 客户端，不读取进程内存、聊天数据库或聊天历史。
- 本机只实现 ENet listener，未公告不存在的 TCP/file/reverse listener；未发聊天、文件或远控请求。
- 原始记录、新身份和私有构建在 Git 忽略目录 `local/nativeclient/`；本文不包含实际 UserID、会话 GUID 或对端资料。

用户授权顺序是：一次初验；初验失败后最多两次诊断/验收；第3次协议成功但用户错过观察窗口后，用户另行明确要求 **“再来一次，已经超过90秒了，不确定”**，第4次才补做 UI 验收。没有在未知结果上自动换标识或无限重连。

## 4. 两次失败及修正

01、02均完成发现与 ENet，收到对端 1000，本机 1000/1018获得传输ACK；但未收到对方1018，对端随即关闭。

第一项明确配置差异是本机将 `MSG` 版本列表留空；普通原客户端声明 `2:1`。修正该声明后，02仍然失败，故**不能将 MSG 修正单独认定为真实问题已解决**。本机按版本协商约束构造的合成回归通过，也不能替代真实结果。

随后在原 EXE 的 `0x669cc0` 握手接收函数中确认了 `INFO/GROUP` 的非空条件：

- `0x66aeab` 将 ASCII `GROUP` 键地址 `0x9eaa38` 用于查找。
- `0x66aee8` 在缺元素时进入失败分支 `0x66c50c`。
- `0x66af09` 在内容长度为0时同样失败。
- 上层 `0x650f70` 将 unpack 失败转为内部下线事件3。

本机实验资料将 GROUP 留空，不符合该约束。改为明确的联系人资料分组标签 `NWT-Go-Test` 后，03、04均成功。这不是 QGROUP_ID，不涉及加入原生群。未复制对端分类或组织资料。

`NewClient`/实验资料构造现会在发包前检查 APP、MSG、NAME、GROUP 非空；回归覆盖这些字段为空时的明确失败，并保留“本机 READY 获ACK但远端未READY”必须判失败的测试。

## 5. 成功运行事实

03：主动发送 type4、1000、1018；完成双向READY后发送应用1016；限时结束发送1017，并完成 ENet DISCONNECT/ACK。

04：按会话排序被动接受对端，收到 type4/1000后发送自己的1000/1018；协议就绪、应用1016和1017/正常断开均成功。

两次运行结果均为：

```json
{"protocol_ready":true,"graceful_exit":true,"discovery_attempts":1,"discovery_sends":1,"unhandled_commands":{}}
```

两次均 `chat_sends=0`。结束后只读端口检查确认本机 UDP listener 已释放。没有把 `graceful_exit` 外推为 Windows UI 下线状态已人工核实。
