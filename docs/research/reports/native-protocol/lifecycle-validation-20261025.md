# 2026-10-25 启动与退出抓包：上线、握手、READY 和 QUIT

本文离线分析远程 main 的启动、退出采集，核对原生网络协议时序，修正仅凭端口与包长作出的解释。不操作真实客户端，不发送或重放消息。

## 1. 结论

**本次观察到的上线顺序是：UDP 发现 → ENet 建连 → 二进制节点控制包 type 4 → 双向 1000 `X_HANDSHARK` → 双向 1018 `X_READY` → 3004/3005 群信息同步。** 首个 1000 在局域网 ENet 的分片中，不在公网 TCP 上。

**正常退出的顺序是：1017 `X_QUIT` → ENet ACK → ENet DISCONNECT(data=0) → ENet ACK。** 分别向两个已有对端执行；最后 ACK 后 108.641 秒没有观察到 9011/9012 流量。

公网 TCP 请求实际是明文 HTTP `POST /api/report.php`，Host 为 `report.51nwt.com`，返回 **404**；发生在本地握手与 READY 之后约 59 秒。它不是 1000，不是本次观察到的原生上线前置认证。

这两份包补上了原客户端上线与退出的运行证据，但 **没有实现独立 Go 进程上线，没有捕获 1004/3011，也没有 `recipient_observed`**。不把正常客户端自动启动进入主窗口写成“已恢复账户认证”。

## 5. ENet、分片与二进制节点控制

### 5.1 建连参数

主连接和临时连接的 CONNECT/VERIFY_CONNECT 都可解析出：

- `MTU=1400`，`window_size=65536`，`channel_count=1`。
- 入/出 bandwidth 参数为 0，throttle interval=5000、acceleration=2、deceleration=2。
- CONNECT/VERIFY_CONNECT 使用控制 channel 255；应用数据使用 channel 0。
- peer ID、session ID、sequence 属于当前 ENet 会话；不能从这次抓包复制给下一次进程重启使用。

这些值是实际包中的参数，不是把 ENet 默认值当成观察结果。不是所有 peer 都使用同一个 session ID。

### 5.2 1000 必须先重组

| 分片帧号 | 重组应用帧字节数 | 命令 |
|---|---:|---:|
| 95、96 | 1485 | 1000 |
| 99、100 | 1472 | 1000 |
| 113、115 | 1485 | 1000 |
| 114、116 | 1485 | 1000 |

每组均核对 start sequence、fragment count/number、total length、offset 和无缺口覆盖；重组完成后才解释应用头，再以完整 payload 为单位进行 XTEA 分块解密。四组正文均解析为 `X_HANDSHARK docver="1"`，重新编码后与原密文字节一致。

不能逐 UDP 包解密，也不能因为第一个分片看不到完整 XML 就认定为新的登录加密。

### 5.3 304 字节包有两种传输位置

- UDP 9011 直接承载 `(304, 1/2, 1)` 的发现包。
- 主/动态 ENet channel 0 的可靠数据中承载 `(304, 4, 1)` 的节点控制包。
- 六个 type 4 包与同一发送者的发现包相比，仅 type 字段有差异；**不是 XTEA XML 应用消息**。

本次可核对的二进制字段：

| 偏移 | 长度 | 已观察内容 |
|---|---:|---|
| `0x00` | 4 | 大端总长度 304 |
| `0x04` | 4 | 大端 type：发现 1/2、ENet 节点控制 4 |
| `0x08` | 4 | 大端 version 1 |
| `0x18` | 2 | 大端端口 9011 |
| `0x1a` | 2 | 大端主 ENet 端口 9012 |
| `0x1c` | 2 | 大端主 TCP 端口 9012 |
| `0x1e` | 65 | NUL 终止用户标识字段；本报告不保存其值 |
| `0xa5` | 2 | 大端动态 ENet 端口；本机为本次实际绑定的 55777 |

这没有恢复整个 304 字节结构的全部语义。尤其不能把未知字段填零后直接宣称可独立上线。

### 5.4 动态端口交换是什么

C0 从动态端口向 P1、P2 的已广告动态端口分别建立两条临时 ENet peer：

- 与 P1 共 16 个 datagram，与 P2 共 20 个，共 36 个。
- 含 CONNECT、VERIFY_CONNECT、ACK、BANDWIDTH_LIMIT、304 字节 type 4 节点控制和 DISCONNECT。
- 这四条临时 peer 没有承载 1000；实际 1000 在两个持续的主端口 9012 会话中。

结合静态分析中反向 ENet listener 的存在，这些包提供了反向/临时连接选择的运行线索；本次只把已观察到的临时建连与释放写成事实，不命名为独立认证服务。

## 6. 1000 与 1018 的字段含义

### 6.1 握手内容

四个 `X_HANDSHARK` 都包含 `FEATURE`、`INFO`、`NET`，版本字段为 `MAJOR=3, MINOR=4, BUILD=3055, APP=1`。字段集合与静态 packer 一致。

没有在这些握手字段中发现密码、口令摘要、challenge 或 token。握手会公布用户资料和能力，但收到一个身份字符串不等于已经验证身份真实性；组织标识的可信校验、身份冲突处理仍未恢复。

### 6.2 XML 的端口整数有字节序问题

本机发出的两个 1000 的原始 XML 中：

| XML 字段 | 原始十进制文本 | 16 位交换后 | 本机采后端点 |
|---|---:|---:|---:|
| FILE_TRAN_TCP_PORT | 13603 | 9013 | 9013 |
| FOLDER_TRAN_TCP_PORT | 13859 | 9014 | 9014 |
| FILE_TRAN_TCP_REVERSE_PORT | 34539 | 60294 | 60294 |
| FOLDER_TRAN_TCP_REVERSE_PORT | 34795 | 60295 | 60295 |
| LAN_UPDATE_HTTP_PORT | 35051 | 60296 | 60296 |

因此，本样本这些字段的十进制文本表示的是网络序 16 位值在小端进程中作为整数打印的结果。**不能把 XML 的 `13603` 直接当作实际监听端口。** 对端的主传输字段也分别交换到 9013/9014；本机字段进一步得到独立端点快照印证。

### 6.3 READY 明确公布 USER_ID

四个 1018 的结构均为：

```xml
<X_READY docver="1"><USER_ID>发送者原始标识</USER_ID><PARAM>0</PARAM></X_READY>
```

每个 READY 的 USER_ID 都与**该发送者**发现包 `0x1e` 处的标识一致。不是本地递增路由编号，也不是接收者 ID。此处只归档对应关系，不归档真实标识。

### 6.4 3005 存在厂商 XML 标签错配

四个 3005 都能用固定密钥解密并重新编码为原密文，但严格 XML 解析失败：开标签 `<QGROUP_INFO_VER>` 被闭合为 `</GROUP_INFO_VER>`。

原 EXE 内对应 UTF-16 字面量也分别存在于文件偏移 `0x5e9944` 和 `0x5e996e`。因此这不是 XTEA 错误，也不是缺少分片；不能通过“重解密”或自动修补原始报文掩盖它。codec 应保留正文原始字节，业务 XML 兼容规则须另行明确。

回归测试只使用不含用户、群资料的合成错配正文；不把真实群信息写入 fixture。

## 7. 公网 HTTP 是什么

- 启动 #600：TCP SYN；#603：一个完整的 945 字节 TCP payload。
- 请求：`POST /api/report.php HTTP/1.1`，Host `report.51nwt.com`。
- Content-Type：`application/x-www-form-urlencoded`；Content-Length=805。
- 唯一表单字段为 `json`，其中 JSON 字段名是 `app`、`build num`、`corp id`、`corp time`、`ip`、`mac`、`major num`、`minor num`、`name`、`sex`、`type`、`user id`、`user list`。只记录字段名，不复制字段值。
- #607：HTTP 404；294 字节 TCP payload，包括 146 字节 HTML 正文；没有返回认证成功、session 或原生 1000。
- 原 EXE 中也存在 `report.51nwt.com` 与 `/api/report.php` 的 UTF-16 字面量，文件偏移分别为 `0x5e0366`、`0x5e0386`。
- #2025：服务器约 60 秒后先发 FIN；客户端进入 CLOSE_WAIT。退出采集中的本机 FIN 是同一 TCP 连接的后续关闭。

这些字节直接支持“报告接口”解释。不能仅凭出现公网 IP 和身份资料就把它命名为账号认证，更不能复制该请求作为独立进程登录步骤。

## 8. 退出：1017 与 ENet DISCONNECT 是两层

退出请求墙钟时间为 `09:32:26.7894957+08:00`；第一个 QUIT 在 `09:32:27.023060+08:00`。下表相对退出抓包第 1 包计时：

| 帧号 | t（秒） | 方向 | UDP 正文 / 应用帧字节数 | 内容 |
|---|---:|---|---|---|
| 133 | 8.9597086 | P2 → C0 | 8 / 无 | ENet PING，控制 channel 255 |
| 134 | 8.9946176 | C0 → P2 | 10 / 无 | 对该 PING 的 ENet ACK |
| 151、152 | 10.6111539 / 10.6111902 | C0 → P1/P2 | 39 / 29 | reliable channel 0，1017 `X_QUIT` |
| 153、154 | 10.6623995 / 10.6765240 | P1/P2 → C0 | 10 / 无 | 对 QUIT 的 ENet ACK，channel 0、sequence 15 |
| 155、156 | 10.7115864 / 10.7116539 | C0 → P1/P2 | 12 / 无 | ENet DISCONNECT，channel 255、sequence 11、data=0 |
| 157、158 | 10.7725544 / 10.7775556 | P1/P2 → C0 | 10 / 无 | 对 DISCONNECT 的 ENet ACK |
| 254、255 | 12.3427917 / 12.3429798 | C0 ↔ 报告服务器 | TCP，无应用字节 | 本机 FIN+ACK、远端 ACK |

QUIT 明文：

```xml
<X_QUIT docver="1" />
```

应用帧是 29 字节，头 `0000001d 000003f9`；正文 21 字节，前 16 字节加密、最后 5 字节 `31 22 20 2f 3e` 不变。两个实际应用帧相同：

```text
0000001d000003f9078c112e9c8bc952426afbd748cd5e933122202f3e
```

Go 重新编码的 SHA-256 与两个捕获帧均为 `e3d9ffad610091bbce78c3342a6962d949ee1eaf2771e53dfc7027915afb3bae`。新增 `TestCapturedQuitFrame` 验证逐字节一致。

ACK 按反向端点、channel、sequence 和回显 sent-time 关联。第一个 QUIT 到最后一个 ENet ACK 为 **0.1664017 秒**；这不是进程退出总耗时，也不说明所有端口都在 0.2 秒内关闭：公网 TCP 的 FIN 发生得更晚，进程消失则由源时间线单独记录。

### 8.1 静默窗口能证明什么

- 退出文件全程 UDP 9011 为 0；本次没有观察到 9011 下线广播。
- 9012 共 10 个 datagram；最后 ACK #158 之后，文件仍记录 1001 个其他包、持续 **108.6410275 秒**，其中没有 9011/9012。
- 本次原客户端是主动、正常退出，不能代替拔网线、崩溃、丢 ACK 或进程被强杀的故障实验。
- 因而只记录“此窗口内无后续包”，不写成“协议离线感知完全依赖单播”或“从不探测重试”。

## 9. 最小独立实现还缺什么

已取得实际字节依据的部分：

1. 304 字节发现/节点控制包的部分字段、实际 9011/9012 和动态 ENet 端口。
2. 主会话 ENet CONNECT/VERIFY_CONNECT、channel 0、可靠序号与分片重组。
3. 固定密钥业务帧、双向 1000、1018、1016、1017 的顺序。
4. 群信息同步 3004/3005 及厂商 XML 错配。
5. 正常退出的应用 QUIT 与传输断开。

尚不能跳过的部分：

- 本机合法身份及资料的提供方式、304 字节未知字段、组织/身份冲突规则；不把捕获的真实身份复制给新进程冒充已完成初始化。
- 临时/反向 ENet peer 与主会话的去重、选择、释放规则；实际可靠传输的版本兼容和状态管理。
- 1018 以后是否已满足发送 1004/3011 的全部条件、MSG_ID/时间/富文本生成与群成员权限语义。
- 没有新增 1004/3011 发送样本、业务 ACK 或独立接收证据，不能宣布完整网络 PoC 已成功。

接下来应按上述缺口完善离线契约和状态机，而不是继续追查这个已确认为报告请求的公网 HTTP 流。真实发送仍须另获具体目标、完整正文与次数授权；不会凭这两份已完成的采集记录自动连接或重放。
