## 3. 业务帧与 CMsg 对象

### 3.1 线上业务帧

`0x67b3b0` 的四个栈参数为路由值低/高 32 位、业务命令号和可写 NUL 终止正文地址。x86 指令确认四参数 `ret 0x10`，并排除了旧反编译签名错位的影响。[N01]

设 XML 的 UTF-8 字节数为 `n`，不计终止 NUL：

| 字节偏移 | 长度 | 字段 | 规则 |
|---|---:|---|---|
| `0x00` | 4 | `total_length` | `htonl(n + 8)`，包含本字段和命令号 |
| `0x04` | 4 | `command` | `htonl(command)`；1004 为 `00 00 03 ec`，3011 为 `00 00 0b c3` |
| `0x08` | `n` | `payload` | 第 3.3 节处理后的 XML 字节；不附带 NUL，不作长度补齐 |

`0x7076ac` 是 Winsock `htonl` 导入跳板；`0x707070` 依次复制 4、4、n 字节。输入先用 `strlen` 计长，然后原地加密，再复制进帧。[N01、N02]

**第二个 32 位字段是命令号，不是序列号。** 消息标识 `MSG_ID` 属于 XML 业务字段；ENet 自己的可靠传输序列字段属于更外层，均不能加进这个 8 字节头。

### 3.2 进程内 CMsg

| 对象偏移 | 含义 |
|---|---|
| `+0x00` | CMsg 虚表 |
| `+0x08` | 内部事件类型；业务数据为 1，连接上线/下线事件为 2/3 |
| `+0x10/+0x14` | 64 位本地路由编号 |
| `+0x64` | 已分配的业务帧缓冲地址 |

对象分配 `0x68` 字节、缓冲初始分配 `0x200` 字节。**这两个数都不是线上固定包长，也不是最大消息长度。** CMsg 的路由值和虚表没有序列化进第 3.1 节的帧。[N01、N03]

### 3.3 正文加密与密钥来源

已确认 `0x598e50`/`0x598f40` 是一对 **XTEA 32 轮加密/解密函数**：[N02、N04]

- 分组 8 字节，两个数据字按大端解释；四个密钥字也按大端解释。
- 增量 `delta=0x9e3779b9`；32 轮后的和为 `0xc6ef3720`。
- `0x599030` 逐个处理完整 8 字节分组；解密对应 `0x599080`。
- 独立分组处理，不使用 IV、不使用分组间反馈、不填充；**最后 `n % 8` 字节保留明文**。
- `0x67b47e` 将固定地址 `0x9ef1c8` 传作密钥；该地址完整 16 字节为 `38617366686a406b372a323068626c61`，ASCII 为 `8asfhj@k7*20hbla`。[N05]
- 帧头不加密，密钥不是本条路径中按密码、挑战或 TLS 握手派生出来的。不能据此推断应用内所有其他协议也使用此常量。

Go 实现只复现这种兼容格式，不把它用于新协议的安全设计。抓包时应先按总长度重组完整业务帧，再解密 payload；不能在每个 TCP 分段边界重新开始分组，也不能把裸 ENet UDP 数据直接当成业务帧。[N01、N04、N09]

## 4. 出站队列到 socket

### 4.1 消费过程

1. `0x650f20` 按业务类型/命令从 `0x656900` 的工厂取 packer，调用 pack 后将 CMsg 放入节点管理器 `+0xfc` 的出站队列。[N06]
2. `0x652470` 取出出站队列，使用 CMsg `+0x10/+0x14` 在管理器 `+0x30` 的连接表中查找路由，把内部类型 1 的消息转交连接对象 `+0x1c` 的队列。找不到路由不能凭空产生线上目标。[N15]
3. `0x6531a0` 遍历活动连接，调用收包 `0x652780`、发送消费 `0x652a50`，处理失败后释放连接。[N08]
4. `0x652a50` 取走 CMsg `+0x64` 的帧缓冲，交给连接的 `CDataSenderT<ISocket>`。`0x5a63b0` 维护当前缓冲、总长度与已发送偏移，处理部分写入；Winsock `10035` 表示当前不可写，不是送达。[N07、N09]

注意：管理器 `+0x100` 是接收/事件队列，`0x650f70` 从该队列读取、由帧 `+4` 取命令，再调用 unpack；不能把两条队列的方向交换。[N10]

### 4.2 TCP 与 ENet

- TCP：`CTcpSocket` 的连接方法 `0x5ad570` 调 Winsock ordinal 4，即 `connect`；发送 `0x5ad690` 调 ordinal 19，即 `send`。[N11]
- ENet：`0x5ab240 → 0x5ac570 → 0x5ac5d0 → 0x70afb0` 建立 peer；`0x5ac510 → 0x70ac80` 创建 host。[N12]
- `CENetSocket` 虚表 `0x9e1254` 的 `+0x2c` 是 `0x5acb70`；该方法调用 `0x709c80(data, len, 1)`，再调用 `0x70a870(peer, 0, packet)`。这对应 reliable packet、channel 0 的发送结构。[N13]
- ENet 的 Windows UDP 写入函数为 `0x70b8f0`，在 `0x70b969` 调 `WSASendTo`。**不能跳过 ENet 外层、将加密 XML 帧直接 `sendto` 到 ENet 监听口。** [N14]

这些是静态调用关系；后续[三份采集](lifecycle-validation-20261025.md)已观察到两个局域网原生 ENet 会话，包括实际 CONNECT/VERIFY_CONNECT 与 channel 0 业务分片。原生 TCP 业务会话和其他部署的中转方式仍未运行验证。

## 5. 节点发现、握手与心跳

### 5.1 地址和端口从哪里来

`CNodeMsgMgr::Init`（`0x6506b0`）创建 TCP listener、ENet listener 和反向 ENet listener。主要 TCP/ENet listener 首次尝试本机 `9012`，失败后以端口 0 再创建；反向 ENet listener 直接用端口 0。随后通过 socket 查询实际端口，保存在管理器状态，再放入节点信息。[N03、N15]

`0x657920` 为 `CNodeListMgr` 创建 UDP socket，将本机地址和其初始化参数中的端口写入 `sockaddr_in` 后 `bind`；绑定失败再尝试端口 0。这是**本机发现 socket**，不是连接认证服务器。[N16]

`0x657da0` 发出固定 `0x130` 字节的 hello，向已知地址发送，并向 `255.255.255.255` 发送广播；`0x6582a0` 使用 `recvfrom` 读发现响应。`0x659050` 写入发现包长度、类型、版本、本地节点信息及传输端口。[N17]

已核实的发现包前三个大端 32 位字段是：总长度 `0x130`、调用方指定的类型、版本 `1`。它是二进制发现包，**不是第 3 节的 XML 业务帧**。发现包余下字段、所有类型含义和初始化端口的完整配置来源尚未整理成可实现契约，不能凭构造函数中另一个 `9011` 缺省值硬写成“服务器端口”。IPMsg 的 `2425` 属于另一套兼容协议。

`0x653540` 根据发现状态选择主动 `connect ip` 或等待对端 `connect me`，使用节点记录中的地址与 TCP、ENet、反向端口建立连接。[N12、N17]

### 5.2 上线不等于账号认证

工厂 `0x656900` 区分内部类型 `2 → COnlinePacker`、`3 → COfflinePacker`、`1 → 依业务命令选 packer`。类型 2/3 是本地事件；没有证据表明它们就是线上命令 2/3。[N18]

业务命令 **1000** 的 packer 是原程序拼写 `CHandsharkPacker`，`0x669370` 生成 `X_HANDSHARK docver="1"`：[N15]

- `FEATURE`：版本和应用、消息、文件、原生群、离线消息等能力标识。
- `INFO`：`CORP_ID`、`CORP_TIME`、`NAME`、`GROUP`、组织资料、状态及显示设置。
- `NET`：文件、目录传输的 TCP/ENet 与反向端口，以及局域网升级 HTTP 端口。

完整 XML 模板及参数处理保留在 [N15] 的批量项 `0x669370`；接收解析为 `0x669cc0`。[N09]

[后续启动采集](lifecycle-validation-20261025.md)已完整重组四个双向 1000；随后双方交换 1018 `X_READY`，其中 USER_ID 与发送者发现包 `0x1e` 处标识一致、PARAM=0。实际握手 XML 的端口十进制文本还需做 16 位字节交换，才对应本机监听端口；不能直接拿 XML 数值连接。

这个模板没有账户密码字段。本轮搜索发现不少 `Password`/`Login` 字符串来自 SMTP、SSH、代理或锁屏功能，**没有把它们误认成本业务协议的认证**。搜索覆盖及原始命中记录保存在 [N19]。尚未证明组织标识如何校验，也没有证明部署中完全不存在另外的认证服务；当前不能实现或宣布“服务器登录成功”。

### 5.3 心跳与断线

- `0x60fac0` 创建命令 `1016`；packer `0x674b50` 生成 `<X_HEARTBEAT docver="1" />`，仍经第 3 节的业务帧构造。[N20、N07]
- `0x5bcc80` 发送前更新对应记录时间；`0x5bd0c0` 检查活动记录：接收时间差小于 120000 ms 时，如果发送时间差大于 59999 ms，则调用 `0x5bcc80`；达到 120000 ms 时进入 `0x6135e0` 断开处理。[N21]
- `0x674c00` 解包 `X_HEARTBEAT`，再经 `0x671540` 分派本地回调；尚未证明独立的应用层心跳响应命令，不能自行添加一个响应包。[N22]
- TCP/ENet 连接失败、超时、节点重新发现分别有本地处理；没有确认单一的“服务器重连命令”。`0x653d70` 的 30000 ms 比较属于待处理连接状态，不是业务发送的自动重试间隔。[N22]

后续正常退出采集已确认 1017 `<X_QUIT docver="1" />`，其 ENet ACK 之后才发送 ENet DISCONNECT(data=0) 并等待传输 ACK，见[逐帧时序](lifecycle-validation-20261025.md#8-退出1017-与-enet-disconnect-是两层)。正常退出不是崩溃、丢包或拔网线实验，不能据此填补异常重连规则。

独立实现仍需从发现、连接创建、握手接收到断开事件逐项建立状态模型。不能为掩盖缺失字段而自动重连或重放 1004/3011。

## 6. 64 位路由编号与群拓扑

`0x651dd0` 创建连接对象时，将管理器 `+0x1c8/+0x1cc` 的计数值复制到连接 `+0x10/+0x14`，随后递增计数并处理进位；管理器初始化时将计数设为 1。[N03、N15、N23]

`0x61b150` 在群管理器 `+0x94` 的用户映射中查找，找到时返回节点 `+0x30` 的 8 字节值，否则返回 0。[N24]

路由写表处理 `0x61b770` 调用 `0x61cc30` 获取记录 `+0x30`，`0x61b95b/0x61b965` 将低/高 32 位写入；`0x61cc30` 具有找不到时插入记录的分支。调用者包括 `0x618ff0`、`0x619eb0`，不是由群 ID 自行计算一个路由值。[N25]

群发送 `0x617600 → 0x61b350` 遍历成员，对每个成员调用 `0x61b150`，只将非零路由加入集合，再逐路由调用 `0x6114f0` 生成 3011。[N26]

因此：

- 该编号只在当前进程的连接管理中有意义，不应从旧进程日志复制给独立进程。
- 用户 ID、群 ID、本地路由编号和网络端点是四种不同标识。
- **这条已分析的群发送路径按成员投递到对等连接，不是把群 ID 交给一个固定服务器并由它广播。** 是否还有离线/跨网段服务是另外的问题，未由本轮静态分析排除。

## 7. 1004 / 3011 业务正文

已确认的模板：[N02]

```xml
<X_SEND_MSG docver="1"><MSG_ID>...</MSG_ID><RECEIPT>...</RECEIPT><MSG>...</MSG><MSG_TIME>...</MSG_TIME><OFFLINE>...</OFFLINE><HIDE_RECORD>...</HIDE_RECORD></X_SEND_MSG>
```

```xml
<X_QGROUP_SEND_MSG docver="1"><QGROUP_ID>...</QGROUP_ID><MSG_ID>...</MSG_ID><MSG>...</MSG><HIDE_RECORD>...</HIDE_RECORD></X_QGROUP_SEND_MSG>
```

单聊命令为 1004，群聊为 3011；二者按所选连接发送，帧头没有独立目标用户字段。`MSG` 来自既有富文本/内容序列化，不把用户输入直接拼进 XML；`MSG_ID` 的新建规则、`MSG_TIME` 单位、各 flag 的选取及独立进程的合法身份初始化仍须单独证明，当前离线 PoC 不替调用者构造这些业务值。

1005 ACK 与 1006 receipt 已有历史 packer 证据，但 **ACK、receipt、socket 返回值或 ENet 排队成功都不替代独立接收观察**。

## 8. PoC、抓包及验收

### 8.1 当前可运行的 PoC

见 [nwtprotocol 使用说明](../../../tools/nwtprotocol.md)。它通过 stdin/stdout 编解码业务、节点和 ENet 数据，支持 JSON Lines 分片重组与已观察双向顺序的回放；不导入 `net`、不实际发现节点、不监听、不连接、不登录、不读取客户端配置、不发送。

测试包括 XTEA 零密钥/零明文的标准已知答案 `dee9d4d8f7131ed9`、固定样本密钥的独立参考向量、1..24 字节分组尾部、UTF-8、连续帧、错误长度、截断、预算和命令 I/O 错误。固定密钥合成用例 `command=1004, payload=12345678x` 的整帧为 `00000011000003ec8564d0424f8cfe2278`，来自独立 Python 参考计算。这些是合成验证，不是原客户端输出或抓包一致性验证。另已实际运行两个独立 Go 进程，通过 stdin/stdout 对合成中文/emoji 正文编解码，往返一致；没有建立网络连接。

### 8.2 后续一次受限采集

抓包范围应包含**已批准的客户端与实际通信节点**，不能只过滤一个尚未确认的“服务器”而漏掉发现和 P2P：

1. 确定 Windows 本机、客户端样本身份、网卡、允许记录的节点/服务器及采集时段。
2. 先被动观察；若需要捕获启动握手，再明确允许一次正常退出/启动及其影响。不由分析工具触发其他功能。
3. 记录 UDP 发现、TCP/ENet 建连和首个 1000；若观察心跳，采集时段应足以覆盖 60 秒检查。保存原始 capture 摘要和时间，不在公开文档保存用户资料。
4. TCP 先重组字节流；ENet 先解析外层可靠包/分片，再抽取业务帧。比对总长度、命令号、固定密钥解密后的 XML 和未加密尾部。
5. 若还要对照 1004/3011，必须另获具体目标 ID、**完整正文、每种调用次数**的明确授权；使用新的唯一测试记录，不重放历史任务。
6. 独立 Go 真实连接实验须先补完发现/身份/握手契约，单次发送、不自动重试。记录连接/排队事实后保持 `delivery=unknown`；独立接收端确认正确目标、发送者和本次新增正文，才记录 `recipient_observed`。

静态调查阶段没有 capture；后续已核对[稳态采集](capture-validation-20261025.md)与[启动、退出采集](lifecycle-validation-20261025.md)。原客户端心跳与 QUIT 可由 Go 逐字节往返；启动 1000/1018 的交换已有实际采集依据。仍无独立进程上线、1004/3011 或接收报告，不生成虚构的登录成功或送达结果。
