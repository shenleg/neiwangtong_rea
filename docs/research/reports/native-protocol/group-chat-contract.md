# 原生群资料同步与群聊静态契约

本文用于实现独立节点的已加入群资料恢复：说明正常对端提供的群ID、群名、完整成员、功能版本及3011投递前提；不恢复主动入群接口，不记录真实群资料。

## 1. 可实现结论

- **3002是群资料推送，3003是群资料加完整成员推送；3004/3005只交换群资料，不能取得成员。完整成员请求/回复是3006/3007。** 3001是邀请答复，不是群列表请求。[G02、G03]
- 群成员为`<USER><ID name="成员名称">成员用户ID</ID>...</USER>`。用户ID在元素正文，不在`name`属性；不得按名称、IP或显示顺序推断ID。[G03]
- 3007的`RET`是标记组合，不是“0成功”：原生正常成员回复为20（`0x14`），非成员资料回复为12（`0x0c`），对端自己不在群回复10（`0x0a`）。带资料条件是`RET & 4 != 0`，请求者成员条件还需`RET & 0x10 != 0`。[G04]
- 原生`FEATURE/QGROUP`、`FEATURE/QGROUP_MSG`均支持版本集合`{1,2}`，可声明`2:1`；各群消息XML的`docver`仍为1。版本声明不代替本机在群中的事实。[G05]
- **3012确切为`X_QGROUP_OTHER_INVITE`，不是3011回执。** 本次未恢复3011确切业务回执；不能把1005自动归为群送达，也不能虚构3012 ACK。[G02、G09]
- 3011必须按完整成员逐个解析本地路由并投递。单对端模式仅能在“完整成员中除本机外恰好只有当前已握手对端”的情况下覆盖整群；有任何其他成员而无其路由，就不能报告整群已提交。[G08]

这里的“对端”是正常身份握手后的原生对等连接，不是中央群服务器。请求和答复均沿选定连接发送，群ID在XML内。[G02]

| 3002 | `X_QGROUP_PUSH_INFO` | 资料持有者向连接对端推送一群资料；没有成员 | `0x9edc20`；`0x671d38`引用模板，`0x671e3e`压入3002 |
| 3003 | `X_QGROUP_PUSH_USER` | 资料持有者向连接对端推送一群资料及成员 | `0x9edf30`；`0x672f8c`引用模板，`0x6730a6`压入3003 |

| 3005 | `X_QGROUP_REQ_INFO_RSP` | 对端答复3004；无成员 | `0x9ebc98`/`0x9ebd60`；`0x665c56`/`0x665f95`压入3005 |

| 3012 | `X_QGROUP_OTHER_INVITE` | 群管理的其他成员邀请操作；不是聊天ACK | `0x9eb620`；`0x662c31`引用模板，`0x662c7a`压入3012 |

### 3.1 公共INFO与精确的错误闭合标签

3002、3003、3005带资料分支和3007带资料分支使用下列同一字段布局。以下保留样本原文的错误闭合标签，不能原样交给严格XML解析器。[G02]

```xml
<INFO><QGROUP_ID>%s</QGROUP_ID><QGROUP_NAME>%s</QGROUP_NAME><QGROUP_MASTER>%s</QGROUP_MASTER><QGROUP_INTR>%s</QGROUP_INTR><QGROUP_ANN>%s</QGROUP_ANN><QGROUP_INFO_VER>%llu</GROUP_INFO_VER><QGROUP_USER_VER>%llu</QGROUP_USER_VER><QGROUP_ALLOW_OTHER_ADD>%llu</QGROUP_ALLOW_OTHER_ADD><QGROUP_PHOTO_MD5>%s</QGROUP_PHOTO_MD5></INFO>
```

- `QGROUP_ID`、`QGROUP_MASTER`为原样保留的标识；`QGROUP_NAME`为群名；`QGROUP_INTR`为简介；`QGROUP_ANN`为公告；`QGROUP_PHOTO_MD5`为群照片摘要字段。
- `QGROUP_INFO_VER`、`QGROUP_USER_VER`是十进制无符号64位版本值。接收业务分别比较INFO对象`+0x98/+0x9c`、`+0xa0/+0xa4`，成员版本不同时发3006；不要改用本机时间。[G06]
- `QGROUP_ALLOW_OTHER_ADD`按样本`%llu`保留无符号数；本报告不恢复修改它的管理权限或其他取值语义。
- 兼容方式是仅在3002/3003/3005/3007的`INFO`内，将**紧随`<QGROUP_INFO_VER>`十进制数值的那个**`</GROUP_INFO_VER>`更正为`</QGROUP_INFO_VER>`，再执行严格XML解析和字段校验。正确闭合形式也可接受。其他标签错误、嵌套错误、重复字段仍应失败；不启用通用宽松XML，不对任意正文做无范围字符串替换。
- 接收器按`QGROUP_INFO_VER`名称查找：3002的`0x6723a7`、3003的`0x67368c`、3005的`0x666744`、3007的`0x65f633`。厂商自有解析器如何容忍错闭合未完整恢复；上面的局部更正是独立实现的明确兼容规则，不是假称恢复了厂商XML库行为。[G02]

### 3.2 完整根结构

下文`INFO`代表3.1原样字段块，`USER`代表3.3成员块；这两个占位符不是线上标签。[G02、G03]

```xml
<X_QGROUP_INVITE_RSP docver="1"><QGROUP_ID>%s</QGROUP_ID><USER_NAME>%s</USER_NAME><ACTION>%u</ACTION></X_QGROUP_INVITE_RSP>
<X_QGROUP_PUSH_INFO docver="1">INFO</X_QGROUP_PUSH_INFO>
<X_QGROUP_PUSH_USER docver="1">INFOUSER</X_QGROUP_PUSH_USER>
<X_QGROUP_REQ_INFO docver="1"><QGROUP_ID>%s</QGROUP_ID></X_QGROUP_REQ_INFO>
<X_QGROUP_REQ_INFO_RSP docver="1"><RET>%u</RET><QGROUP_ID>%s</QGROUP_ID></X_QGROUP_REQ_INFO_RSP>
<X_QGROUP_REQ_INFO_RSP docver="1"><RET>%u</RET><QGROUP_ID>%s</QGROUP_ID>INFO</X_QGROUP_REQ_INFO_RSP>
<X_QGROUP_REQ_USER docver="1"><QGROUP_ID>%s</QGROUP_ID></X_QGROUP_REQ_USER>
<X_QGROUP_REQ_USER_RSP docver="1"><RET>%u</RET><QGROUP_ID>%s</QGROUP_ID></X_QGROUP_REQ_USER_RSP>
<X_QGROUP_REQ_USER_RSP docver="1"><RET>%u</RET><QGROUP_ID>%s</QGROUP_ID>INFOUSER</X_QGROUP_REQ_USER_RSP>
```

3002根下只有INFO；3003根下只有INFO、USER。不存在另一个顶层群列表、消息ID或目标用户字段。3005/3007带资料时顶层`QGROUP_ID`与`INFO/QGROUP_ID`是两个位置；独立实现应要求相同，不能让其中一个覆盖另一个。[G02]

### 3.3 成员USER

样本`0x9eaef4`的原始宽字符串模板是：

```xml
<ID name="%s">%s</ID>
```

3003的`0x672cc5–0x672d42`分别取成员项的ID与名称，经`0x659a80`处理后，以“名称参数、ID参数”的格式化顺序写该模板，连续拼接到USER。3007在`0x65e9e8`复用同一模板。3003解包`0x673c2c–0x673d39`匹配`ID`节点，以节点正文取ID、以`name`属性取名称。[G03]

```xml
<USER><ID name="成员甲">user-id-a</ID><ID name="成员乙">user-id-b</ID></USER>
```

这是一次成员集合序列化，不含分页号、增删操作码或“后面还有一页”的字段。独立实现可以将成功3003或3007的USER作为该版本的一份完整成员快照，但不能凭一群的快照声称已枚举本身份所有群。成员名称不是投递依据，投递只使用原样ID。[G03、G06、G08]

### 3.4 3007 RET与成员授权事实

`0x65e784–0x65e787`在RET的`0x4`未置位时使用简短回复模板；`0x65f068–0x65f06a`在解包时做相同选择。原生请求处理入口`0x619cc0`的三个正常分支为：[G04]

| RET | 形成条件/实际作用 | 独立节点处理 |
|---|---|---|
| 10 (`0x0a`) | `0x619d1d`判定答复方本机不在群，`0x619d98`提交10 | 没有INFO/USER；不建立可发送快照 |
| 12 (`0x0c`) | 答复方在群，但请求者不在成员中；`0x619e20–0x619e35`计算 | 有INFO/USER，但不能把请求者当成已加入 |
| 20 (`0x14`) | 答复方在群且请求者是成员；同一段以`成员判断*8+12`计算 | 有INFO/USER；还应核对快照包含自己的原样ID |

`0x619e08`调用`0x61b470`取得该群成员，`0x619e50`通过`0x610e30`发回3007。成员关系不是根据请求里自报的名称判定：请求只有QGROUP_ID，业务从连接路由经`0x61b1c0`确定请求者身份再检查。[G04]

建议可发送快照至少满足`RET & 0x14 == 0x14`、群ID相同、自身ID在成员集合内、资料来源是当前已核对身份的连接。这里后几项是独立实现的外部输入校验规则；不宣称厂商有完全相同的校验函数。

## 4. 独立节点如何取得自己已加入的群

1. 复用已经验收的独立身份、发现和1000/1018握手，显式宣告`QGROUP=2:1`、`QGROUP_MSG=2:1`，不复制Windows客户端身份。[G05]
2. 从**当前正常对端新收到的**3002/3003取得群ID和群名。3003带USER，可验证本机ID；3002没有成员，不能凭它宣布已经取得完整成员。[G02、G03]
3. 对每个已知群ID向同一对端请求一次3006，接收3007。3004/3005可更新INFO，但不能替代这一步；不要为了获得成员而反复请求3004。[G04、G06]
4. 检查RET、原样群ID、自己的成员ID，并保存来源对端和两个版本值，形成一群的快照。3002或后续INFO表明成员版本变化时，使旧成员快照不可用于“整群已覆盖”的判断，再按明确策略请求新3007。[G04、G06]
5. 不需要主动加入：用户已确认独立Go身份在`qun3`中，这提供任务背景；实际群ID与完整成员仍由此独立身份当前收到的正常协议资料取得，不能从名称猜ID或从历史私有日志恢复。

原生资料事件`0x618410–0x618609`维护“用户到群”的索引，并在`0x6184f5`、`0x6185de`对相关群发3004；3002接收`0x618ec8–0x618ef1`发现成员版本不同会发3006。这证明正常对端同步既有群资料的路径，不要求新增邀请或加入接口。[G06]

**尚未证明的是“空本地状态的新节点每次上线必收到全部已加入群的完整列表”。** 本次没有恢复一个无群ID的列举所有群请求，也没有证明3002/3003的首次推送保证。当前连接收到的3004含已知群ID，也可作为待核实ID种子，再以3006/3007核实；不能因没收到推送而断言本机没有群，不能把一份快照当成全部群资料。该种子处理是独立实现方案，非新增发送授权。[G06、G09]

## 5. FEATURE版本的静态依据

`0x9b7510`是宽字符串`1:2`。原生初始化`0x43fa40–0x43fa70`将其解析到群功能集合`0xb29154`，`0x43fa93–0x43fac3`将同一值解析到群消息集合`0xb29170`。`0x5b9da0`解析版本集合，`0x5b9f50`迭代集合、转十进制并用冒号拼接。[G05]

全局用户对象基址为`0xb28dd0`；`0xb28df0`是其`+0x20`的用户ID字符串，不能拿它计算能力集合偏移。群功能getter `0x5b8e30`读取用户对象的`+0x384`（集合wrapper `0xb29154`的内部tree），群消息getter `0x5b8e60`读取`+0x3a0`（wrapper `0xb29170`的内部tree）；`0x5b991a/0x5b9958`分别放入握手对象`+0x134/+0x150`。`0x669370`的握手packer按模板`0x9ec510`将其放到`QGROUP/QGROUP_MSG`；反向解析`0x5b916b–0x5b918c`也将握手`+0x134/+0x150`转回用户对象`+0x384/+0x3a0`的版本集合。已验证MSG也通过同一集合构造与serializer声明`2:1`；因此独立实现声明相同支持集合`2:1`，不是把输入常量`1:2`误当固定顺序要求。[G05]

本次未恢复完整版本协商拒绝状态机，不把“版本字符串非空”当作群同步或3011收发成功。

## 6. 3011接收与整群投递的界限

已验证模板与解包入口继续沿用前报告：packer `0x679c10`、unpacker `0x679f30`，模板`0x9eeea0`。[G07、G08]

```xml
<X_QGROUP_SEND_MSG docver="1"><QGROUP_ID>...</QGROUP_ID><MSG_ID>...</MSG_ID><MSG>...</MSG><HIDE_RECORD>0</HIDE_RECORD></X_QGROUP_SEND_MSG>
```

本次定点核对了unpacker：根名比较`0x67a04d`，QGROUP_ID、MSG_ID、MSG分别在`0x67a069`、`0x67a11d`、`0x67a1aa`查找；MSG_ID以十进制64位解析；HIDE_RECORD在`0x67a261`查找且允许缺省0；`0x67a321`经`0x67a4a0`分发回调。[G07]

**解析器本身并不完成成员检查。** 后续业务回调的完整“群存在、发送者成员、本机成员”判定未恢复。不能把XML能解析、回调被调用或已知群ID等同于对端接受消息。本轮按后续任务要求停止扩展此部分，不编造通过条件。[G07、G09]

已有N26：`0x617600 → 0x61b350`遍历本地群成员，`0x61b150`解析路由，将非零路由加入集合后逐路由调用`0x6114f0`。因此一个peer不是群广播服务器。最小单peer实现只能在完整成员快照证明“全部非己成员都由该peer覆盖”时发送；离线、未知或未连接成员不能被静默省略后称为整群投递。传输提交和独立接收观察必须分别记录。[G08]

## 7. 回执结论与必须保留的未知

- 3012已由模板和压入命令常量共同排除，它的完整模板是`<X_QGROUP_OTHER_INVITE docver="%u"><QGROUP_ID>%s</QGROUP_ID><USER>%s</USER></X_QGROUP_OTHER_INVITE>`。[G02]
- 本次没有找到并证明一个专属3011 ACK命令、字段和业务产生位置；也没有证明3011复用`1005/X_SEND_MSG_ACK`。已有1005单聊证据继续只证明其原范围。实现可保留未知命令观察，但不能把相同MSG_ID的任意回执解释成整群送达。[G09]
- 必须解决或明确限制的缺口：首次穷尽群枚举的保证；3011接收业务成员条件；确切群业务回执。当前单peer还必须核实整群非己成员是否都能覆盖，否则需要多peer路由实现。
- 本轮没有实际请求群资料、发送3011或执行真实验收。静态契约不产生真实上线、聊天或自动重试授权。
