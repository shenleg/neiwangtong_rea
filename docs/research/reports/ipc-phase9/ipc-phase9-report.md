**窗口歧义已在操作者手动关闭附加窗口后消失，现有 386 完整只读预检通过；准确的 QGROUP_ID 尚未取得，首次发送测试准备未完成。**

## 2. 窗口歧义及关闭后的复检

### 2.1 复现与人工操作

首先从唯一运行进程的映像路径调用现有程序，执行模式为 **Windows 386、无 `-send`**：

```bash
GOARCH=386 go run ./cmd/ipcexperiment -exe 'C:\实际安装目录\ShiYeLine.exe'
```

首次实际输出：

```text
拒绝选择 HWND: assessment=ambiguous candidates=2
exit status 1
```

这一步在首次 Resolve 处停止，不能把它记为完整身份预检通过。PID 9656，运行中的同名进程只有一个，未选择两个候选中的任何一个。

随后读取窗口元数据。第一次外部 Python 包装按系统 GBK 解码探针 UTF-8 输出，发生 `UnicodeDecodeError`；修正为显式 UTF-8 后再次只读采集，此时已经只有一个候选。操作者随后确认，他们手动关闭了附加窗口。

**本次操作和观测支持“附加窗口造成候选歧义，正常关闭后恢复唯一候选”的判断。原始第二个候选在成功采集前已经消失，没有取得其 HWND、owner、style、尺寸及创建关系，不能补造这部分信息。** 本轮未要求重新打开附加窗口来补采，也未自动关闭任何窗口。

### 2.2 当前全部 SkinDialog 窗口

采集主机时间：`2026-10-22T18:06:50.518519Z–18:06:50.5331386Z`。会话日期为 2026-10-23；保留主机原始时间，不修改系统时钟。窗口标题已省略。PID/HWND 仅为本次生命周期标识，不是配置值。

| HWND | `0x2036E` | `0x30344` |
| 类名 | SkinDialog | SkinDialog |

| parent（GA_PARENT） | `0x10010` | `0x10010` |

| 分类 / 是否候选 | main_candidate / 是 | hidden_owner_suspect / 否 |

关系为 `0x2036E → owner/root_owner 0x30344`；隐藏 owner 自身无 owner。它符合 `0x4029d0` 中“先创建隐藏 owner，再把 HWND 传给主窗口 DoModal”的静态依据（第五阶段 N18，`ev_b0e215670dc529323c5c94c2fffd0ad6d267b489b86df2f1446bb95e939f7a90`）。通用类注册与创建分别见 `0x54fd20`、`CSkinDialog::Create @ 0x524890`（N15、N16）。

这里的“创建关系”是当前 owner 关系与已有静态创建过程的比较。EnumWindows 不提供窗口创建时间或创建调用栈，不能据此声称观察到了运行时创建顺序，也不能证明候选的 C++ 对象就是 CMainDialog/业务处理器 `0x449c60`。两个 SkinDialog 不等于两个候选；当前隐藏 owner 不计入候选。

### 2.3 关闭后的重复采集和 Resolve

在操作者确认关闭后，再用现有 386 探针采集 5 次，间隔 1 秒：

```bash
GOARCH=386 go run ./cmd/windowprobe -format json -count 5 -interval 1s -label phase9-after-manual-close
```

- 主机 UTC 时间：`2026-10-22T18:09:54.511756Z–18:09:58.5711407Z`。
- 5 次均为一个进程、一个候选、`unique_unverified`，没有读取问题。
- 4 个相邻比较均为 `stable_unique_unverified`，没有身份或外观变化；整体 stability 同值。
- 随后显式启用已有只读 `TestResolveAuthorizedCandidate`，386 连续两次 Resolve 及返回前复核通过，返回 PID 9656、HWND `0x2036E`、owner `0x30344`。
- 再次运行无 `-send` 的 386 实验程序，完整预检通过。

去标题、去实际 EXE 路径的扫描保存在本机临时目录 `windowprobe-phase9-*` 的 `after-manual-close-386.redacted.json`，不提交 Git。本文包含关键结果，不依赖临时文件长期存在。

## 3. 唯一授权 QGROUP_ID：获取、核验和填写

### 3.1 已有资料是否给出了获取步骤

**后续静态研究更新**：已找到 `data\qrp` SQLite 群元数据和 `QGroupInfo_<内部身份标识>.Name → QGroupId` 对应关系，详见[群 ID 获取报告](../qgroup-id/qgroup-id-report.md)。该报告提供只查询授权群元数据的只读方案，不是读取聊天记录或凭据；Windows 实际验证和真实 ID 仍未完成。以下保留阶段九当时的资料状态与准备要求。

**没有经过验证的客户端菜单、命令或工具获取步骤。** 已有资料只给出了以下要求和语义：

- [历史报告第 3、7 节](../gateway-static/gateway-report.md)：QGROUP_ID 是原生逻辑群字符串，不是群显示名称或 IPMsg 分组；无法从授权可见信息确认时先人工补足，不读取进程内存或解密数据库。
- [IPC 契约第 3.4 节](../../ipc/ipc-contract.md)：`group_id → 0x4ee740 → 0x4edfc0` 查现有群表，再进入 `0x4b9c80 → 0x617600`。依据为 E23-I、E25-G1、E25-G2。
- `X_QGROUP_SEND_MSG` 构造函数 `0x679c10` 包含 `QGROUP_ID`（E20），但静态字段名称不是实际测试群的 ID，也不是允许抓取或发送原生网络数据的授权。

### 3.2 合法获取与核验

由操作者或测试群管理员完成，避免向报告写入私人群信息：

1. 在正常登录客户端中检查该授权测试群可见的属性信息。**只有明确标为内部群标识且能确认对应原生 QGROUP_ID 的值才可使用。** 本项目没有验证该版本界面一定提供此字段，不虚构菜单路径。
2. 若界面不提供准确内部 ID，请测试环境管理员或厂商提供适用于 3.4.3055 的官方群元数据、受支持的管理导出或接口说明，并确认其字段对应 QGROUP_ID、对应的正是这一个授权原生群。仅有群名、截图中的名称或来源不明的编号不够。
3. 在仓库外的私有准备记录中记下唯一 ID 的原始值、来源、核验日期、对应测试群及授权范围；不记录密码、令牌或聊天内容。由管理员和操作者核对，不尝试发送来验证 ID。
4. 确认当前发送账号有该群正常成员资格和发送权限，独立接收账号在正确群中就绪，群内没有未授权成员。本轮这些条件已经由操作者人工确认，实际测试前仍需保持成立。
5. 没有可核实来源则停止。禁止由群名称计算/猜测 ID，禁止枚举候选 ID 或通过试发寻找目标；不读取进程内存、聊天数据库、凭据或批量群列表。

### 3.3 现有程序的填写位置与限制

现有唯一绑定位置为 `cmd/ipcexperiment/main.go`：

```go
const authorizedGroupID = ""
```

取得并明确授权一个真实 ID 后，才在本地把空字符串替换为**这一个原样 ID**。没有 `-group-id`、环境变量目标、列表参数或批量发送入口，不增加这些入口。真实 ID 不提交 Git，不写进公共报告。

当前 `cmd/ipcexperiment/main_test.go` 的 `TestAuthorizationNotBound` 有意断言该常量为空。在取得 ID 前必须保留此测试；未来绑定时须同时将这项“未授权阶段”断言改为针对新授权状态的测试，并保留空授权、无效输入、人工确认与单次限制的回归测试，重新测试和构建。**不能只改常量后忽略失败测试，也不能删掉测试来启用发送。** 本轮未修改常量或测试，未创建可发送的授权构建。

现有实验只接受 1–199 字节 ASCII 字母、数字、`_`、`-`；这是本地输入子集，不是厂商 ID 语法或容量。真实 ID 若不符合要求，停止并另行分析，不 trim、不转换大小写、不截断、不换用群名。
