# 第七阶段：IPC 契约恢复与首发测试准备

本文记录接收端长度复核、已提取发行文件的生产者搜索及首次授权群聊测试的缺项；不是可执行的发送协议。

## 1. 结论与范围

**未达到“可以编写最小测试发送器”的标准。** 已确认文本接收路径不按 `cbData` 限制三次 UTF-8 源读取，转换缓冲区按查询结果动态分配；没有恢复生产者的字段容量、结构总大小、填充或 `cbData` 写入依据。窗口阶段六的稳定候选不能代替业务入口验证。

- 样本：内网通 3.4.3055，`/root/reverse-lab/extracted/app/ShiYeLine.exe`，x86，ImageBase `0x400000`。
- SHA-256：`e7caef3fe744f9fe6ba90dd1d53b7e64241cb54020a8bf37be5e756e2fe881b1`，本轮独立计算与历史一致。
- 复用 [IPC 契约](../../ipc/ipc-contract.md)、[第五阶段报告](../ipc-phase5/ipc-phase5-report.md) 的索引及相关单条证据；没有一次加载所有历史证据包。
- 用已有 REA 反编译与指令、独立 GNU objdump 限定地址解码交叉检查。字节扫描记录和独立 objdump 记录均不冒充 REA Evidence。
- 本轮未执行客户端、发送消息、改 EXE、注入、读取聊天数据库或凭据；未实现发送器。未重新反编译 `libcef.dll` 等无关组件。
- “已确认”均指静态事实；Windows 平台文档、阶段六历史运行记录和本轮静态证据分开引用。

## 2. `0x449c60` 的结构访问与控制流

### 2.1 完整函数范围与其他业务分支

历史 E22-I 的 Ghidra 函数体包含 `0x449c60–0x449fe5`、`0x449ffe–0x44a27f`；`0x449fe1` 的 free 跳板被标为 no-return，导致中间缺口。独立 [focused-objdump.json](focused-objdump.json) 的 `handler` 记录从文件解码 `[0x449c60, 0x44a280)`，确认缺口 `0x449fe6–0x449ffd` 只是原分支的局部清理，没有新增文本长度判断。文本分支本身不经过该缺口。

| 指令位置 | 对输入结构/载荷的访问 | 所属路径及结论 |
|---|---|---|
| `0x449ca0` | `[EBP+0xc] → EDI` | 取得 `COPYDATASTRUCT *` |
| `0x449ca9–0x449caf` | 检查 EDI 是否为零 | 只保护结构指针，不保护 `lpData` 或其长度 |
| `0x449cb4` | `[EDI] → EAX` | 读取 `dwData`，随后按业务常量分流 |
| `0x449cc2–0x449cc9` | 将结构指针传给 `0x443ce0` | 仅 `0x0fe1c10b` 启动/激活分支；本轮不将该辅助函数行为外推到文本分支 |
| `0x449d53–0x449d56` | 取 `[EDI+8]`，检查载荷非空 | 仅 `0x0fecf10b` 分支 |
| `0x449d75 / 0x449de6` | 读取其载荷 `+0xc8`；元素起点 `+0xcc`，步长 `0x208` | 另一业务的计数/列表访问，不是文本第四字段或文本容量 |
| `0x44a04b–0x44a04e` | 取 `[EDI+8]`，检查载荷非空 | 仅 `0x0fecf10e` 分支 |
| `0x44a06c / 0x44a0e0` | 读取其载荷 `+0xc8`；元素起点 `+0xcc`，步长 `0x208` | 同样不能套到文本业务 |
| `0x44a119–0x44a124` | 比较 `0x0fecf10f`，取 `[EDI+8] → EBX` | 本文文本业务入口；随后没有 `TEST EBX`，也没有读取 `[EDI+4]` |
| `0x44a24a–0x44a255` | 将原结构传给 `0x522c70` | 该基类对文本常量不进入任何载荷读取分支，见下文 |

本函数完整文件解码中没有直接读取 `COPYDATASTRUCT+4` 的指令。其他业务的载荷空指针检查与列表读取是真实存在的，但**不属于文本路径**；不据它们增加文本字段或长度要求。也不声称其他分支的所有间接被调用函数都不使用 `cbData`。

### 2.2 文本路径逐项核对

| 阶段 | 实际汇编 | 判断 |
|---|---|---|
| 选择器 | `0x44a124` 取基址 EBX；`0x44a130` 调用 `0x44cbd0` | 直接使用原始基址，没有预先定长拷贝 |
| 目标值 | `0x44a16c` 恢复基址；`0x44a174 ADD EBX,0x64`；`0x44a178` 调用 | 只计算起点，不代表目标容量为 200 |
| 正文 | `0x44a1b1` 恢复基址；`0x44a1b9 ADD EBX,0x12c`；`0x44a1c0` 调用 | 没有计算 `cbData-0x12c` 或正文末尾 |
| 宽字符串复制 | `0x44a140 / 0x44a185 / 0x44a1cd` 比较对象 `+0x18` 与 8，再于 `0x44a156 / 0x44a19b / 0x44a1e3` 调用 `0x408420` | 比较的是转换结果的存储方式，不是传送数据的长度 |
| 业务调用 | `0x44a1f9–0x44a20f` | 栈上传目标值，EDX 传正文，ECX 传选择器；三个均为宽字符串对象，不继续传原始载荷 |
| 清理与基类 | `0x44a217–0x44a255` | 清理局部宽字符串后传原结构给基类；没有第四个文本字段访问 |

历史伪代码将 EBX 隐式参数显示为 `unaff_EBX`，不会正确显示三个源偏移；`param_2 + 8` 的伪类型表达式也不能当成 C 结构元素指针运算。字段偏移以以上实际指令为准。[E22-P、E22-I、E22-U]

基类 `CSkinDialog::OnCopyData @ 0x522c70` 在 `0x522cbc` 读取 `dwData` 后，只为 `0x7d1–0x7d8` 等类型进入各自的 `cbData/lpData` 分支。文本常量依次比较不等，最终 `0x523114 → 0x523161`，不读取 `+4/+8`，返回内部 0。上层映射正常窗口结果仍为 1。[第五阶段 N8、N9、N22、N23、N25、N26]

**长度结论**：已复核的文本分发、处理及基类路径，没有基于 `cbData` 的源长度或指针边界验证。这里不能推出 `cbData=0`、任意长度或某个最小长度是合法协议。

## 3. 三个字符串的读取、分配和复制

### 3.1 `0x44cbd0` 的两次转换

独立解码的源参数 EBX 与 E22-U 的反编译一致：

| 指令 | 参数/行为 | 与长度有关的含义 |
|---|---|---|
| `0x44cbfb–0x44cc05` | 初始化结果对象：容量 7、长度 0、首个宽 NUL | 这是宽字符串对象初始化，不是源 UTF-8 缓冲区 |
| `0x44cc09–0x44cc18` | `MultiByteToWideChar(65001,0,EBX,-1,NULL,0)` | 查询包含终止 NUL 的目标宽字符数；源按 NUL 读取，不受 `cbData` 约束 |
| `0x44cc1e–0x44cc22` | 保存返回值 N，为 0 则到 `0x44cc87` | 第一遍失败时保留空结果，未生成业务错误响应 |
| `0x44cc24–0x44cc35` | N 乘 2，乘法溢出时把分配请求置为全 1，再调用 `0x87f2ab` | 依据转换结果申请临时存储，不是固定消息长度；未将溢出处理解释为业务拒绝协议 |
| `0x44cc3c–0x44cc43` | 对 N×2 字节清零 | 临时宽缓冲区，不是清零完整 IPC 结构 |
| `0x44cc4f–0x44cc5b` | `MultiByteToWideChar(65001,0,EBX,-1,temporary,N)` | 第二遍仍以 NUL 扫描源；N 只限制目标宽字符写入，不能当作源读取上限 |
| `0x44cc61–0x44cc79` | 扫描临时宽 NUL，将算出的长度与数据交给 `0x408330` | 这一步读的是转换结果，不是 `lpData` 后续字段 |
| `0x44cc7e–0x44cc9b` | 释放临时存储后返回结果对象 | 独立文件解码确认 `free` 后有返回代码；不能据 no-return 注记说成功路径会终止进程 |

第二遍调用返回后直接扫描临时宽字符串，没有检查该遍的 EAX，也没有读取 `GetLastError` 来向调用方报告转换原因。第一遍分配/清零顺序和失败异常行为不构成可靠错误协议；本轮未触发或测试内存分配失败。

Microsoft 对 `MultiByteToWideChar` 的规定：`cbMultiByte=-1` 处理输入至终止 NUL，返回计数含该 NUL；`cchWideChar=0` 查询所需宽字符数。`CP_UTF8,dwFlags=0` 不启用严格错误拒绝，Vista 以后以 U+FFFD 替换非法序列。[W1] 这是平台规则，不是本轮运行结果；完整业务显示仍未验证。

### 3.2 小字符串存储不是 IPC 容量

`0x408420` 初始化一个容量 7 的空宽字符串，扫描传入宽 NUL，再调用 `0x408330`。后者比较长度与对象容量，必要时调用 `0x408140` 增长，复制宽字符并补 NUL：

- `0x408386–0x4083a5`：长度与 `0x7ffffffe`、当前容量比较，超出当前容量时进入增长函数。
- `0x4083ed–0x408410`：按宽字符数×2复制，写入长度并补宽 NUL。
- `0x4081a6–0x4081b3`、`0x40822a–0x408240`：增长路径为新容量加终止符申请空间，保存新指针、容量、长度和 NUL。

因此这里存在固定大小的**局部字符串对象及内联小字符串存储**，但没有发现用 100/200 字节定长 UTF-8 数组接收源字符串。不能把对象大小、内联容量、栈帧 `0x5b8` 或库实现的 `0x7ffffffe` 当作正文业务上限。完整增长/分配异常处理不属于已恢复的消息错误返回协议。

### 3.3 边界及后续字段的明确结论

| 问题 | 结论 |
|---|---|
| 源是否先进入固定 UTF-8 缓冲区 | 已检查路径没有；原始偏移直接交给转换函数 |
| 接收端是否设源读取上限 | 没有看到按字段容量或 `cbData` 的上限；两遍均 `cbMultiByte=-1` |
| 是否可能读过 `cbData` 边界 | 是：若该字段的首个 NUL 不在传送区内，代码仍会要求继续读取；可表现为区外读取或访问异常，本轮不运行此类载荷 |
| 是否有独立第四字段 | 在已复核文本正常路径及基类该分支没有发现；未证明生产者结构没有尾部保留数据 |
| 是否能认定正文以 `cbData` 结束 | 不能；已知终点只有首个 NUL |
| 是否恢复字段容量、总长、填充 | 没有；接收端的动态分配不能证明生产者怎样分配和写入 |

## 5. 已确认的必要安全输入条件

**目前只能给必要条件，不能给“满足即可安全发送”的充分条件或完整载荷。**

对传送字节区 B、长度 C 和三个起点 `o=0/0x64/0x12c`：

1. 结构和载荷指针有效，实际数据连续，在调用期间不被改写；接收端不替发送方验证这些条件。
2. 每个 `o` 均位于传送区内；从该处开始必须有首个 NUL，且该 NUL 的偏移严格小于 C。只有正文起点可达而正文 NUL 不可达是不够的。
3. 若某字段 NUL 前字节数为 `n_o`，则 `o+n_o < C`。这是包含关系，不是建议选择某个 C，更不是生产者固定总长的证据。
4. 各字符串写入不能覆盖另一个起点；使用合法 UTF-8、禁止嵌入 NUL 是首次测试设计限制，不把非法输入交给客户端试错。
5. 首次用例仅 `group_id`、一个独立确认的授权原生群 ID、固定非空 ASCII 文本 `NWT-GW-AUTH-TEST-0001`；不允许列表、名称选择器或任意文本。

上述条件没有回答字段官方容量、尾部字段、清零/填充、完整总长和正文业务上限。不得把“正文末尾的算术偏移”提升为 `cbData` 合法值，也不通过追加大量零尝试规避未知结构。

## 6. 结合阶段六的首次群聊测试条件

运行依据来自 [windowprobe 阶段六记录](../../../tools/windowprobe.md#阶段六手动状态测试记录与标准)，不是本轮新执行：Windows 10 19044，amd64 与 386，每种架构每种状态 5 次，共 60 次状态快照。单实例显示/托盘隐藏/恢复时身份稳定；附加对话框时三个候选并拒绝；重启后旧 Target 被拒绝，明确获取新 Target 后复核通过。托盘隐藏的 `minimized=false` 不能当标准最小化通过。

首次测试前必须分别满足：

- **协议**：获得可核实、匹配版本的生产者/接口定义，恢复字段容量、总长、NUL、填充和 `cbData`，完成复核。当前未满足。
- **隔离与授权**：正常登录的两个授权测试账号，仅含授权成员的一个原生群，明确实际发送授权；不读取历史聊天。本轮没有发送授权。
- **样本身份**：正常路径、版本和哈希符合目标；探针的路径/创建时间/存活检查不能替代文件真实性检查。
- **当前窗口**：只使用已测的单实例正常显示状态，操作者关闭附加对话框后重新采集，唯一候选、无读取问题，调用前重新 Resolve；歧义或身份变化即停止，不复用本文历史 HWND/PID。
- **入口验证**：阶段六仍为 `unique_unverified`，未证明候选绑定 CMainDialog/`0x449c60`；应在另行授权的隔离验证中建立，不对多个候选逐次试发。正常界面发送成功也不单独证明外部 IPC 入口。
- **系统访问**：同一交互 session/desktop、同用户与完整性级别；实际 IPC/UIPI 可达性未验证，不提权、不改消息过滤。386 首测只是减少跨位数变量；阶段六跨位数只读成功不等于跨位数 IPC 成功。
- **一次性调用**：固定一个群和一条文本，调用前记录尝试，仅一次、有期限、不自动重试、不转单聊；超时可能已产生业务，不能据无返回再发一次。
- **结果判定**：分别保存 API 返回、错误码、窗口结果和耗时；本机观察与独立授权接收端观察分开。`LRESULT=1` 不算送达；无接收证据为 `unknown`，只观察一个接收方也不代表全群收到。

标准最小化、多轮重启、登录界面、多真实实例和跨会话均不在阶段六真实验证范围。首次测试不需要假定这些场景已通过，应排除这些场景。

## 7. 剩余风险、停止条件与下一阶段

仍不可证明的条件：

1. 文本生产者结构及 `cbData` 的合法值、固定或可变长、字段容量、填充和尾部约定。
2. 正文业务上限、分配失败与业务异常的完整处理、非法 UTF-8/特殊字符的最终显示。
3. 精确群 ID 语法、完整角色/禁言规则、登录/连接状态与下级状态字段的对应关系。
4. 候选 HWND 与业务处理器的运行绑定、实际 UIPI/IPC 可达性、异常/退出/超时的实际表现。
5. 无 ACK 返回协议条件下的实际投递，以及最终检查后 HWND 销毁/复用的时间竞争。

**建议停止对本接收端的重复静态逆向，不扩大到无关 Chromium 组件。** 本轮仍有转换/复制细节的新证据，但它们不能提供缺失的生产者长度；继续重复已有查询不会恢复从未使用的结构声明。
