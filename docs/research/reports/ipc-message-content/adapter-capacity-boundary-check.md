# Adapter 容量边界与最大载荷离线验证

> 后续运行结果：用户之后另行授权的261003字群聊/私聊验证出现客户端卡顿、退出及持续重试报告，见[异常与恢复记录](../ipc-phase12/custom-max-body-abnormal.md)。本文保留此前离线结果，不把它作为真实可用上限。

本文记录 2026-10-24 对当前 Adapter 内容预算边界和 Windows 386 跨进程传送的离线测试，不是内网通真实接收上限报告。

## 1. 结论与执行范围

**当前 Adapter 对无 URL、无换行的重复常见汉字正文，接受 261003 个汉字，拒绝 261004 个汉字。** 对应被接受的 UTF-8 正文为 783009 字节，WM_COPYDATA 最小载荷为 783310 字节。

Windows 386 独立接收 fixture 已对 `group_id` 和 `user_id` 两种选择器完整接收上述 783310 字节，逐字节比较一致。fixture 是测试程序自己创建的进程和窗口，不是内网通客户端；该结果不能证明客户端会联网发送、完整显示或送达同样长度。

用户在了解离线结果及当前客户端单次边界验证范围后，明确选择“保留离线边界结果”。因此：

- 本轮没有向真实客户端发送任何最大长度或超长消息，没有创建真实发送尝试记录。
- 没有逐级增加真实消息长度、扫描边界、二分试发、重发或改变消息过滤。
- 当前真实独立接收成功范围仍是[500 汉字五段，群聊 LF 和私聊 CRLF 各一次](../ipc-phase12/custom-500-newlines-confirmation.md)。

## 2. 按内容区分边界

不含 ASCII 点号的非空正文只有一个普通片段，按[已证明的内容预算](refined-body-bound.md)有：

```text
完整转义 JSON 上界 = F + 446 + 501 = F + 947
共同预算 = 261950
所以 F <= 261003
```

`F` 是正文值经过 JSON 字符转义与外层替换的长度，不含片段界定引号；UTF-8 字节数、字符数、UTF-16 单元和 F 不是同一个量。

以下每项均指表中给定字符的连续重复，不含 URL、换行或其他字符；数量不包含 NUL：

| 正文 | Adapter 最大接受重复数 | UTF-8 正文字节数 | 边界处上界 | 多一个字符的上界 |
|---|---:|---:|---:|---:|
| 常见汉字 `中` | 261003 | 783009 | 261950 | 261951，拒绝 |
| 普通 ASCII `x` | 261003 | 261003 | 261950 | 261951，拒绝 |
| emoji `😀` | 130501 | 522004 | 261949 | 261951，拒绝 |
| 双引号 | 37286 | 37286 | 261949 | 261956，拒绝 |
| ASCII 空格 | 43500 | 43500 | 261947 | 261953，拒绝 |

这不是厂商最大长度表，只是当前保守校验算法对这些确定输入的接受边界。换行、密集 URL 或其他转义字符必须按实际内容另算，不能拿“261003 个字符”当作统一规则。特别是 URL 很多时需要额外计算片段固定开销。

## 3. 新增回归测试

### 输入预算边界

`internal/ipc/message_test.go` 的 `TestMessageCapacity` 覆盖：

- 261003 / 261004 个 `中` 的接受与拒绝。
- 261003 / 261004 个 `x` 的接受与拒绝。
- 130501 / 130502 个 `😀` 的接受与拒绝。
- 37286 / 37287 个双引号，以及 43500 / 43501 个空格的接受与拒绝。
- 非空/UTF-8/NUL 检查、控制字符成本、密集 URL、换行兼容和转换后计数仍继续验证。

这些纯逻辑测试不查询窗口，不向真实客户端发送。

### Windows 386 最大载荷 fixture

`internal/ipc/platform_windows_test.go` 新增 `TestCrossProcessMaximumPayload`：

1. 用正式正文校验接受 261003 个 `中`。
2. 分别构造 `group_id` 和 `user_id` 载荷，确认实际长度都是 783310。
3. 使用既有 `receiverFixture` 创建独立测试进程和隐藏窗口。
4. 调用正式 `sendOnce` 向这个测试窗口传送一次，确认 API 完成、LRESULT 有效、未超时。
5. 比较接收的全部字节、业务 dwData 和发送方窗口存在性。

大载荷经过 JSON/Base64 回报后超过 stdout 管道容量，因此父测试并发读取回报，避免 fixture 自己阻塞同步 WM_COPYDATA 处理。该并发只涉及测试回报通道，不修改正式发送逻辑。

该测试在 amd64 下明确跳过真实发送部分；386 下两个选择器分别通过。超过预算一个字符的输入只验证本地拒绝，不调用 Win32。

## 4. 实际运行结果

先单独运行 386 最大载荷 fixture，两个选择器均确认：

```text
fixture完整接收783310字节，不代表内网通已发送或接收
```

随后执行 amd64 和 386 的全部项目测试及 vet：

```bash
GOARCH=amd64 go test -count=1 -timeout 45s ./...
GOARCH=amd64 go vet ./...
GOARCH=386 go test -count=1 -timeout 45s ./...
GOARCH=386 go vet ./...
```

全部通过。最后一次运行的 `internal/ipc` 包耗时为 amd64 2.737 秒、386 8.845 秒。未修改正式容量算法、目标配置、客户端或历史记录，未自动提交或推送。
