### 2.1 源边界不由 cbData 自动保证

从正文起点到首个 UTF-8 NUL 的字节数若为 `n`，至少要满足 `0x12c+n < cbData`，且终止字节实际位于传送区。内嵌 NUL 会结束当前字符串，后面的输入不会作为同一完整正文继续转换。这里是 NUL 协议的读取终点，不是一个“超长时自动安全截断”的实现。[R1、R2]

选择器与目标的 100/200 字节起点间距，不能证明厂商结构声明为固定数组，也不能反推正文容量。没有发现入口按这两个差值对正文定长复制；这项否定结论只限已复核的入口和转换部分。[R1、R2；对照 `docs/research/ipc/ipc-contract.md:48–67`]

### 2.2 群下级固定容量是本次重要发现

`docs/research/reports/gateway-static/0043-procedure_pseudo_code.json:1` 的 `0x679c10` 可见调用为以下形式。[R17]

```cpp
_swprintf_s(&DAT_00aa84f0, 0x40000,
    L"<X_QGROUP_SEND_MSG docver=\"%u\"><QGROUP_ID>%s</QGROUP_ID>"
     L"<MSG_ID>%llu</MSG_ID><MSG>%s</MSG>"
     L"<HIDE_RECORD>%u</HIDE_RECORD></X_QGROUP_SEND_MSG>", ...);
```

确定的是：**群命令外层 XML 的格式化调用带有固定容量参数**。按当前反编译识别的 `_swprintf_s` 签名，该参数表示目标宽字符元素数，`0x40000=262144`，包含终止 NUL 的空间；不是 262144 个 UTF-8 字节，也不是 262144 个原始正文字符。缓冲区位于全局地址 `0xaa84f0`；真实分配范围和调用约定仍需原始指令/数据交叉确认。[R17]

该函数先通过 `0x659a80` 取得 `%s` 对应对象，格式化后调用 `0x408950`，再向 `0x67b3b0` 交命令 `0xbc3=3011`。尚未恢复 `0x659a80` 返回的正文表示、转义及 `0x408950` 的完整转换行为。现有伪代码没有使用 `_swprintf_s` 返回值，且其后存在 free 的 no-return 误标；不能仅凭该片段决定超长时是错误返回、清空、异常、进程终止、截断还是其他结果，也不能保证调用方能从 IPC 返回识别失败。[R17]

因此本报告**不提供原始正文上限数字，也不指定“保守安全值”**。外层 XML 固定容量是真实限制线索，不是已经完成的正文限制契约。

## 3. 换行、字面反斜杠和其他字符

### 3.1 已确认的替换方向及次数

1. `0x9d1580` 原始字节为 `5c 00 72 00 5c 00 6e 00 00 00`：宽字符串的四个字符依次是反斜杠、`r`、反斜杠、`n`，不是 CR 与 LF。[R5]
2. `0x9b6860` 为 `0d 00 0a 00 00 00`：实际 CRLF。[R6]
3. `0x4c41ec–0x4c423b` 分别用长度 2 和 4 构造这两个宽字符串；`0x4c4240–0x4c4253` 压入第三参数 CRLF、第二参数四字符字面串、第一参数正文，并调用 `CStringHelper::Replace @ 0x568ef0`。[R4]
4. `0x568f00` 查找，`0x568f1c` 按第二参数长度替换为第三参数，`0x568f27–0x568f2f` 继续从位置 0 查找到无匹配，故不是只换首次出现。[R7、R8]

**结果：正文中的每个匹配四字符 `\r\n` 都会变成两个控制字符 CRLF。** 替换发生在公共正文构造之前，因此群与单聊都经过此步骤。每次匹配使该步骤的宽字符串长度减少 2 个 code units；这不代表最终序列化长度也按同样数量减少。[R4–R8]

### 3.2 已有换行和保留字面文本

| 输入 | 该 Replace 步骤的确定行为 | 最终正文是否原样显示 |
|---|---|---|
| 实际 CRLF，字节 `0d 0a` | 不匹配四字符字面串，不被这一替换改变 | 未证明，下级构造/解析仍未完整恢复 |
| 实际 LF 或实际 CR | 该单独字符不匹配这次搜索 | 未证明是否在后续拆分、规范化或序列化中改变 |
| 两字符字面 `\n` 或 `\r` | 单独出现时不匹配四字符模式；该调用不是通用 C/JSON 反转义 | 未证明其他构造步骤是否处理 |
| 四字符字面 `\r\n` | 必定被此步骤改成 CRLF，不能直接原样经过此调用 | 没有已验证的保留机制 |
| 多个反斜杠、额外转义前缀 | 已复核 Replace 是按字符串匹配/替换，没有在该循环中检查“前一个字符为反斜杠则跳过”的逻辑 | 不能把 Go/JSON 的双重转义自动当成客户端支持的保留协议 |

以上逐项根据搜索参数和循环推导，不是运行实验。[R4–R8]

要保留接收端看到的四字符 `\r\n`，必须找到后续能构造该显示值、又不会破坏正文语义的表示方式，或证明本路径不支持无损保留。不能直接推荐多加反斜杠、预先 XML 转义或 CDATA；这些方案尚没有完整下游证据。[R4、R7、R9–R12、R17]

### 3.3 正文构造、XML 与特殊字符

- `0x4b8470` 初始化内容对象，写入 `shiyeline` 等字段，再调用 `0x4b4a70` 和 `0x5f8380`。伪代码的 `local_c0[120]` 是反编译器恢复的局部区域，不能当作 120 字节正文数组；也不能将对象字段值 `10` 当成十字符限制。[R9]
- `0x4b4a70` 的 `0x4b4aa6–0x4b4aae` 在原始片段长度为 0 时直接返回。非空路径调用 `0x4b4480`，再根据结果进入普通追加 `0x5f6260`，或经 `0x4b4930` 拆分、递归处理并调用 `0x5f66c0`。因此此处不是已经证明的“任意文本原样复制”。[R10]
- `0x4b4480` 可见 `CStringHelper::Split`、`0x4b4030` 及若干片段拼接；`0x4b4930` 搜索特定片段并拆分。相关分隔常量、识别规则和返回表示没有完整恢复，伪代码也受 free 误标影响。本报告不猜这些片段是表情、链接或 XML 标签。[R11、R12]
- 外层群 XML 的 `<MSG>%s</MSG>` 没有在模板本身包 CDATA，但 `%s` 来自下级对象；不能据此断言原文 `<`、`>`、`&`、单双引号必定直接进入 XML，不能断言已经自动转义，也不能排除内部内容另有 CDATA。`]]>` 的行为同样未知。[R17]
- UTF-8 转换入口为 `dwFlags=0`，不能宣称客户端严格拒绝所有非法 UTF-8；本轮不测试非法输入。转换成功也只说明进入宽字符串，不证明中文、emoji、制表符或控制字符最后能完整送达/显示。[R2；`docs/research/reports/ipc-phase7/ipc-phase7-report.md:60–83`]

## 4. 仍未确定的问题

1. **原始正文业务上限**：是否先于格式化还有限制，按 UTF-8 字节、UTF-16 code units、Unicode 字符数还是序列化后的长度计算；是否因群/私聊、在线/离线分支不同而变化。[R9–R17]
2. **群固定容量的具体失败语义**：`0x679c10` 中 `0x40000` 的汇编实参、缓冲区真实大小、CRT 超长路径、返回值是否遗漏、下游是否继续用无效结果，以及更低层封包/传输是否另有限制。[R17]
3. **私聊长度限制**：`0x60d930 → 0x650f20` 之后命令 1004 的最终 packer；不能沿用群命令 3011 的容量。[R14–R17]
4. **正文内部表示与膨胀**：`0x4b4480/0x4b4930` 的识别/拆分，`0x5f6260/0x5f66c0/0x5f8380` 的编码及序列化，`0x659a80` 取得的文本是否已转义、编码或包装。[R9–R12、R17]
5. **字符保真**：实际 LF/CRLF/CR、字面 `\n`/`\r`/`\r\n`、多个反斜杠、XML 特殊字符、`]]>`、中文、emoji 的完整转换和接收显示语义；尤其没有四字符字面 `\r\n` 的无损保留方案。[R2、R4–R12、R17]
6. **静态事实与实测范围**：上述缺项不能用固定 ASCII 的成功记录补全；即使静态补齐，中文、emoji、特殊字符与长度边界的独立接收实测仍是另一项需要具体授权的工作。当前不发消息。[`docs/research/ipc/validated-route.md:23,54–60`]
