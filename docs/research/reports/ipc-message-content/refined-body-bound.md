# 按正文内容计算 IPC 序列化预算

> 后续运行结果：满足本序列化预算的261003字样本在真实客户端触发异常报告，用户自行重装恢复，见[异常与恢复记录](../ipc-phase12/custom-max-body-abnormal.md)。本公式不保证客户端稳定，不能直接作为产品可用长度。

本文在远端提交 `6d06c31` 已证明的固定元数据、片段结构和 URL 长度守恒基础上，推导比 512 字节统一限额更实用的容量检查；只做离线计算，不修改发送代码或操作客户端。

## 1. 结论

**不应把 512 字节作为自定义正文的最终限制。** 当前证据可以直接推导按内容计算的上界，无须继续请求 REA：

- 与内容无关的统一保证可提高到 **1665 个 UTF-16 code units**。这不是客户端实际最大值，也不是 1665 个任意 Unicode 码点；常见汉字每个占 1 unit，补充平面 emoji 每个占 2 units。
- 500 个纯常见汉字占 1500 UTF-8 字节，完整转义 JSON 的上界仅 **1447 units**。
- 5000 个纯常见汉字占 15000 UTF-8 字节，上界 **5947 units**。
- 按内容计算并与共同预算 **261950 units** 比较，可允许普通长正文，同时识别大量短链接造成的结构开销。
- 上界超过预算时，只表示该算法不能证明此消息满足容量条件，不能反推客户端实际一定拒绝或崩溃。生产实现应在调用客户端之前明确拒绝此类输入。

上述结论限定于已分析样本的 `0x4b8470 → 0x5f8380` 固定正文构造及两个已定位 XML packer。它证明的是发送端序列化空间，不证明传输、接收显示、离线保存、递归栈使用或实际送达，也不授权真实发送。

## 3. 不重写客户端 URL 识别器的上界

正文边界先要求有效 UTF-8、非空、无嵌入 NUL。为保持输入不被改写，接口继续明确拒绝字面四字符 `\r\n`；实际 LF、CRLF、CR 不转换、不 trim。下面计算使用经过这些边界校验的原文。

定义：

```text
U：正文的 UTF-16 code units 数
D：正文中 ASCII 点号 '.' 的数量
F：所有正文值经过 JSON 字符转义和外层 E 后的内容长度，不含各片段的 JSON 界定引号
T：最终普通文本片段数
L：最终链接片段数
```

已证明最终正文总量守恒，每个值只写入一次，且字符转义逐字符可加，所以 **F 可以直接由原文统计，不需要提前确定片段边界**。片段引号、字段和排版已包含在 446/328 中，不重复计入 F。

### 3.1 片段数的三个约束

每个链接至少消耗 4 个 UTF-16 单元，且至少消耗一个原文 ASCII 点号；非空普通文本至少消耗一个单元。因此：

```text
0 <= L <= min(D, floor(U/4))
T <= L+1
T <= U-4L
```

`T <= L+1` 来自递归分割后普通文本与链接交替的结构：一次分割 k 个非空链接，最多生成 k+1 个待处理子串；对子串归纳即得，不依赖 URL 各不相同。

从而得到：

```text
u(E(J(body))) <= F + 501
                 + max [446*min(L+1, U-4L) + 328L]

其中整数 L 位于 0..min(D, floor(U/4))。
```

不必用 Go 正则模拟客户端的匹配、端口、大小写及递归行为。点号数只是链接数量的上界，可能多算，但不会漏掉符合已恢复正则的链接。

### 3.2 最大值只用计算两次

令 `Q = min(D, floor(U/4))`。函数中两个线性分支的交点为：

```text
L+1 = U-4L
L = (U-1)/5
```

交点之前结构开销每增加一个 L 增加 774；之后每增加一个 L 减少 1456。因此只检查：

```text
a = min(Q, floor((U-1)/5))
b = min(Q, a+1)
```

分别代入 a、b，取较大值即可。一次遍历正文统计 U、D、F，再做常数次整数运算；时间 O(n)，额外空间 O(1)，不递归、不需要生成完整 JSON/XML。

### 3.3 正文内容 F 的精确计数表

| 原文字符 | 对 F 的贡献 |
|---|---:|
| 双引号 | 7 |
| 反斜杠 | 2 |
| 单引号、ASCII 空格 | 6 |
| `&` | 5 |
| `<`、`>` | 4 |
| BS、TAB、LF、FF、CR | 2 |
| 其他非 NUL C0 控制字符 | 6 |
| 其他基本平面字符，包括常见汉字 | 1 |
| 补充平面字符，包括四字节 emoji | 2 |

该表来自已恢复 JSON writer 与外层六项替换。它用于计数，**不是让 Adapter 提前转义正文**。

## 4. 更紧的统一长度保证

即使完全不利用 D 和实际内容 F，也可以比 `457*n+1024` 更紧。

每个链接 host 至少占用 4 个 ASCII 字母、数字或点号。这些字符的值转义成本都是 1，而不是最坏的 7；各链接消耗的原文互不重叠。因此：

```text
F <= 7U - 24L
```

带入 446/328 的分片开销：

```text
u(E(J(body))) <= 7U + 501
                 + max [446*min(L+1, U-4L) + 304L]

0 <= L <= floor(U/4)
```

同样只需检查交点附近两个整数。数值结果：

```text
U=1665：L=333，T=333，上界=261906 <= 261950
U=1666：L=333，T=334，上界=262359 > 261950
```

逐一核对 `1 <= U <= 1665` 均满足共同预算。所以 **1665 units 是这条统一保守公式可以认证的连续长度范围**；1666 处只是该公式不再提供统一保证，不是客户端真实长度边界。

直接以 UTF-16 长度表达比按 UTF-8 字节限额实用：1665 个常见汉字通常为 4995 UTF-8 字节，但仍只有 1665 units。对于超过该范围的正文，按第 3 节实际内容继续计算，不直接拒绝。

## 5. 典型结果

以下均为离线容量计算，不是接收实测：

| 正文 | UTF-8 字节 | U | 完整转义 JSON 上界 | 预算判断 |
|---|---:|---:|---:|---|
| 500 个 `中` | 1500 | 500 | 1447 | 满足 |
| 5000 个 `中` | 15000 | 5000 | 5947 | 满足 |
| 500 个 `😀` | 2000 | 1000 | 1947 | 满足 |
| 16384 个双引号 | 16384 | 16384 | 115635 | 满足 |
| `a.aa ` 重复 333 次 | 1665 | 1665 | 261573 | 满足 |
| `a.aa ` 重复 334 次 | 1670 | 1670 | 262357 | 该上界不能认证 |

最后两项说明：**只按总字节数判断，既会拒绝很长的普通中文，也可能遗漏短 URL 很多时的额外结构开销。** 对于上界超预算的输入，离线算法应明确拒绝，不能实际试发来验证。

无点号的正文一定不含本路径可识别的域名或 IPv4 链接，此时 L=0、T=1，直接简化为：

```text
u(E(J(body))) <= F+947
```

这里的点号指 U+002E，不包括中文句号 `。`；它与客户端正则中的 ASCII `\.` 一致。

## 6. 实现建议与真实验证

- Adapter 不再以 512 字节一刀切；对正文边界校验后，按第 3 节算法计算序列化上界，超过 261950 就拒绝。
- 继续保留原始 UTF-8 字节数用于载荷长度计算；UTF-16 单元数仅用于容量推导，两者不混用。
- 不把理论 XML 容量等同于产品承诺的最大长消息。若要额外限制产品输入大小，应独立命名和说明理由，不再误称为协议上限。
- 本次不引入任意产品限额、不修改发送接口或日志、不创建真实发送尝试。
- 完成 Go 实现与 amd64/386 离线测试后，再另行明确授权具体目标、正文和次数，验证 500 字中文、中文换行等实际接收。没有理由向真实客户端发送接近 XML 缓冲区上限的载荷。
