## 2. 已能确定的数值

### 2.1 单个字符串的转义上界

设一个字符串的有效 UTF-8 内容为 `s`，不含 NUL，字节数为 `n`。只计算该字符串内容经过已确认的 JSON 字符转义与外层六项替换，不包括 JSON 结构、字段名和排版：

```text
内容的最终 UTF-16 units <= 7*n
包含 JSON 两端引号时 <= 7*n + 12
```

原因：

- 双引号是最坏的单字节情况：JSON 先生成反斜杠加引号，外层变为反斜杠加 `&quot;`，共 7 units。
- 空格、单引号分别变为 `&nbsp;`、`&apos;`，各 6 units；`&` 为 5，`<`、`>` 为 4。
- 其他控制字符最多表示为 6 个 ASCII 字符的 `\u00xx`；实际 CR/LF 等使用两个字符的 JSON 转义。
- 未转义的非 ASCII Unicode 字符，其 UTF-16 units 不超过原始 UTF-8 字节数。补充平面字符按 2 units 计算，不按 1 个 rune 计算。
- 两个 JSON 界定引号各变成 6-unit 的 `&quot;`，所以单独计入 12。

原始依据：B12 的 `0x7156d3–0x715854`、B16 的转义常量及 B19 的六项替换顺序。`&` 最先替换，之后新生成的实体不会被再次执行这一项 ampersand 替换。

本次另按该替换表对全部 **1,112,063 个非 NUL Unicode scalar values** 做了合成算术核对，最大单位字节膨胀为 7，达到该值的字符为 `U+0022`。这只核对字符串替换算术，不是客户端运行测试，也不模拟完整客户端 JSON。

### 2.2 群与单聊的共同预算

根据完整报告第 3.2 节，在当前两个 packer、32 字符群 ID、`%llu` 最多 20 位的条件下：

```text
群：   u(E(J)) <= 262143 - 129 - 32 - 20 = 261962
单聊： u(E(J)) <= 262143 - 153 - 20 - 20 = 261950
共同预算：u(E(J)) <= 261950
```

这是完整 JSON 经外层转义后的 UTF-16 预算，不是原始正文限额。它不证明接收端或其他后续路径支持同样长度。

## 3. JSON 构造中的已确认内容和缺项

### 3.1 根字段和字体属性

`0x4b8470` 在 `0x4b84bf` 先调用 `0x5f6ce0` 初始化共用内容对象，再覆盖部分字段，最后于 `0x4b85de` 调用 `0x5f8380`：

- `0x4b84cb–0x4b8502`：版本字段写入长度 3 的常量。
- `0x4b8526–0x4b853b`：调用 `0x592690` 产生标识并复制；历史查询显示成功分支生成 32 个十六进制字符，失败分支使用常量 `0x99deec`。
- `0x4b855b–0x4b8592`：应用字段写入长度 9 的常量。
- `0x4b85bc / 0x4b85c4`：显式启用字体大小属性并写入数值 `10`，不是正文十字符限制。此处根据后续提交 `6d06c31` 的初始化证据更正此前的颜色属性判断；新增字段依据及容量结论见 [更精确的上界推导](refined-body-bound.md)。

`0x5f8380` 写出根字段 `ver / app / id / type`，可选 `ft`，以及片段集合 `dt`：

- `0x5f8603–0x5f8669`：读取对象 `+0x54`，经 `0x593ce0 → 0x4c7530` 转成类型字符串。
- `0x5f86c8–0x5f8a68`：依据标志写字体名、大小、颜色、粗体、斜体和下划线。
- 字体名从内容对象 `+0x60` 的动态宽字符串读取；它是否启用及默认内容要由初始化函数确定。
- 大小、颜色、布尔值各有其格式化路径；不能把字体名也当成一个定长数值。

**未找到 `0x5f6ce0` 的独立实现查询，也未找到 `0x593ce0` 的类型字符串映射实现。** 因而不能证明本 IPC 路径的所有默认字段都是固定短字符串。这里不声称它们一定读取 UI 或任意客户端状态；若初始化函数实际全部写常量，这一缺项就可以直接化为固定开销。

`0x4c7530` 不是新增缺项：历史 `user-id/0024-batch_decompile.json` 已保存其 CP65001 宽字符串转 UTF-8 的实现。

### 3.2 普通文本和链接字段

当前 IPC 分片构造器明确生成类型 0 的普通片段和类型 3 的链接片段。

- 普通片段 `0x5f8ae0–0x5f8c4e`：正文写入 `txt.v`，另有依据子类型填写的 `txt.t`。
- 链接片段 `0x5f90b4–0x5f914b`：主字符串写入 `lnk.v`。

**这两条已识别分支没有把链接再额外写入一份显示文字字段。** 因此不能未经检查就把“链接必然存两份”作为本路径的固定规则。其他类型的 JSON 分支不是本次普通文字入口自动拥有的能力。

两个片段构造器还会调用 `0x5f61b0` 初始化及 `0x5fa0d0` 复制节点。当前没有它们的独立实现；只需核对初始化/复制是否保持已经识别的类型和字段，不应为了这项任务全面逆向所有容器辅助函数。

### 3.3 JSON 排版不是零开销

`0x70dab0 → 0x715b50 → 0x715bf0` 不是仅把各字符串紧凑连接：

- `0x70dae5` 调用 writer 构造 `0x715ab0`。
- 对象分支在 `0x715ed2 / 0x715f6e / 0x71602e` 调用 `0x716540`，在 `0x715eec / 0x716008` 调用 `0x716570 / 0x7165f0`，存在专门的排版/缩进处理。
- `0x715f82–0x715f90` 还追加字段分隔字符串。
- 数组分支 `0x715e4b` 转交 `0x716090`；片段集合的换行与缩进需要计入长度。
- `0x715bab–0x715bb6` 在写完根对象后追加一个常量串。

已有查询没有这些 helper 的独立实现，不能证明当前缩进宽度、数组布局及每节点排版开销的数值。**排版产生的每个 ASCII 空格也会变成 6-unit 的 `&nbsp;`**；不能只给正文字符乘一个转义倍数。

## 4. URL 分片可以得到的条件推导

设进入 `0x4b4a70` 的正文 UTF-8 字节数为 `b`，原始参数长度为 `n`。已知换行字面替换只会缩短，因此 `b <= n`；若接口拒绝字面四字符 `\r\n`，该步骤不改变输入。

当 `0x4b4480` 返回的非空 URL 确实原样存在于当前输入时：

- `0x4b4930` 查找 URL，截取前缀，并删除已经处理到匹配末尾的原文。
- `0x4b4a70` 只递归处理分割后的余串，在相邻余串之间加入链接片段。
- 同一 URL 多次出现时分别消耗各自的原文位置，不会因为递归就重复序列化整篇正文。
- 非空片段数 `S <= b <= n`；各片段主字符串的 UTF-8 总长度不超过 `b`。

这些结论的具体依据是 `0x4b49af / 0x4b49cd / 0x4b49df–0x4b49eb / 0x4b4a0d` 及 `0x4b4b3c / 0x4b4b65–0x4b4b73`。

还缺一项小证据：`0x4b4480` 会从正则捕获组重建 URL，已有资料没有独立导出拼接常量 `0x9d0594`（长度 3）和 `0x99dd74`（长度 1）；`0x4b4030` 只有受 free/no-return 误标影响的伪代码，没有完整有效正则的组合指令。因此尚未把“返回值总是原样子串”写成已完成证明。本次没有发现实际可触发的递归故障，不将证据缺失报告为客户端 Bug。

无需为了宽松上界继续追求 URL 最短长度：在上述原样子串条件成立后，使用 `S <= n` 已足够；若以后想提高允许的正文长度，再计算更紧的片段数。

## 5. 为什么还不能选一个正文限额

可将完整预算分解为：

- `T`：所有正文/URL 字符串内容的 UTF-8 总字节数；URL 条件成立时 `T <= n`。
- `M`：其余 JSON 字符串内容的总 UTF-8 字节数，包括字段名、默认元数据和片段子类型常量，不含引号。
- `V`：JSON 字符串 token 数，包括字段名和值。
- `P`：writer 在字符串之外加入的 ASCII 空格数。
- `R`：其余结构和排版字符的 UTF-16 总长度，例如括号、冒号、逗号与换行。

于是有一个可复核但尚未数值化的界限：

```text
u(E(J)) <= 7*(T+M) + 12*V + 6*P + R
```

缺少初始化与 writer helper 的实现时，`M / P / R` 尚没有足以写入 Adapter 的固定或按片段数计算的上界。只写 `7*n + 一个猜测常数` 会漏掉它们。

因此现在不能宣称“原始正文 4096 字节一定适用”，也没有理由继续寻找统一厂商最大值。下一步只需把这些未知项算成固定开销或每片段开销，再用共同预算 `261950` 选择 Adapter 的明确限额。
