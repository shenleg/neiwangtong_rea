# 内网通 3.4.3055 独立消息网关：只读静态分析与实施建议

## 结论

优先验证“独立 Windows 进程 → 已正常运行的 ShiYeLine.exe 业务 WM_COPYDATA → 客户端既有发送函数”。本轮发现了区别于 CEF IPC 的业务发送入口，静态代码明确支持 user_name、user_ip、user_id、group_name、group_id，并分别调用原生单聊、原生群聊发送函数。这不是已确认的公开 SDK，尚未做运行验证。

IPMsg 独立机器人适合可选的兼容单聊，不满足原生群聊要求。UI Automation 可作为另一种客户端驱动方式，但 SkinUI 控件的可访问性必须动态验证。若“独立”还要求完全不启动官方客户端，目前没有已验证且同时满足原生群聊、不伪造身份、不绕过认证的方案。

- 目标：`/root/reverse-lab/extracted/app/ShiYeLine.exe`。
- 版本字符串：`3.4.3055 @ 0x9b7478`。
- SHA-256：`e7caef3fe744f9fe6ba90dd1d53b7e64241cb54020a8bf37be5e756e2fe881b1`，分析前后一致。
- REA 6.7.0 + Ghidra 12.1.4，x86 PE32，ImageBase 0x400000。
- 仅静态读取和反编译，未运行客户端、未发送消息、未注入、未修改二进制、未读取密钥或用户数据库。
- 复用了上一轮证据；新增查询由独立 REA 进程完成，只给该进程配置了更长启动超时。
- 地址均为静态 VA。FUN_ 名称由 Ghidra 自动生成，不是原始源码符号。

## 1. CIpMsgMgr / OpenIpMsg

### 启用与端口

- `0x4ecb60` 初始化网络配置，其中 IpMsgPort 缺省为 0x979，即 2425。[E1]
- `0x4ecd30` 初始化 OpenIpMsg 缺省值为 1，再读取布尔选项与 XML 中的 IpMsgPort；现有配置可以覆盖缺省值，不能据此声称运行时已经开启。[E2]
- `0x4ed310` 保存相应配置。[E2]
- `0x440aa0` 调用 `0x5ae160` 初始化兼容通道，再应用子网过滤并公告上线。[E3]
- `0x5ae160` 使用 `socket(AF_INET, SOCK_DGRAM, 0)`、bind、非阻塞和广播选项。[E4]
- UI：`res/ShiYeLine/layout/NetworkDialog.xml:9-11`，开关 3102、端口编辑框 3104。

### 发现与身份

- `0x5ae9a0` 构造命令 1 的公告并调用 `0x5b0410`；`0x5b0a30` 处理发现/上线信息并回复命令 3。[E5]
- `0x5b0410` 有网卡、子网及 `255.255.255.255` 发送路径；不得在最小验证中调用此发现广播流程。[E5]
- `0x5afb50` 从 recvfrom 获取来源地址，查询用户表及子网过滤表后才进入解析。[E6]
- `0x5b1c00` 使用来源 IPv4 作为用户表键；不能把它直接当作原生字符串 user_id。[E7]
- `0x5b0940` 构造冒号分隔兼容头，其中有版本、包号、两个身份文本字段、命令和正文；当前客户端的版本字段带 `@shiyeline`。[E8]
- `0x5b30b0` 检查首字段中的 `@shiyeline` 并对匹配值跳到清理出口，避免同类兼容报文进入普通 IPMsg 业务解析。[E9]
- 已检查的兼容文本收发路径没有原生账户认证握手；这不表示可以冒用已有用户。独立机器人必须有单独、明确授权的身份及地址，不复制其他用户的身份字段。
- 解码分支涉及 CP936 和 UTF-8。首个验证使用固定 ASCII 文本，中文兼容性另行验证。[E9、E21]

### 发送和确认

- IPMsg UI 发送函数 `0x50a750 → 0x4bc1e0 → 0x5aed20`，后者构造 0x120，即低位命令 0x20 加 0x100 确认请求标志。[E10]
- `0x5b08b0` 调用 sendto；该调用不能证明对端接收。[E11]
- 接收分发 `0x5b0020` 将低位命令 0x20 交给 `0x5b10e0`。后者在请求确认时构造 0x21，正文关联原包号。[E12]
- `0x5b17b0` 按确认包号删除待确认项；`0x5afb50` 对约五秒未确认项有超时处理。这不能等同用户已读，也未证明无限重试或离线可靠投递。[E6、E12]
- `0x50adc0` 对离线兼容联系人显示离线提示，不等同原生单聊的本机离线队列。[E10]

### 与原生协议关系

兼容协议的 UDP 来源用户表、冒号头、0x20/0x21 命令与原生 CNodeMsgMgr、连接路由 ID、XML 1004/3011 命令是不同路径。IPMsg 的分组文本不是原生 QGROUP_ID。不能向多个 IPMsg 用户单发来冒充原生群消息。

## 2. 原生单聊发送过程

1. `SendMsgButton.xml:2` 的实际子按钮为 22011；2201 是外层发送布局。
2. `0x4f7ad0` 的消息映射将 22011 关联到 `0x50be70`，跳板执行虚函数槽 0x2b0。[E13]
3. CSingleChatLayout 的 0x2b0 槽指向 `0x4fbb50`，其调用 `0x4b76c0` 从编辑控件取正文并构造消息内容，再虚调用 0x294 槽，即 `0x513170`。[E13]
4. `0x513170 → 0x4b9320 → 0x5bc200 → 0x60d930`：处理记录、消息 ID 和目标路由参数，创建命令 1004。[E14]
5. `0x650f20` 使用解析器工厂选取 packer 的发送虚函数，进入 `CSendMsgPacker @ 0x65ca70`。[E15]
6. `0x65ca70` 生成 X_SEND_MSG，含 MSG_ID、RECEIPT、MSG、MSG_TIME、OFFLINE、HIDE_RECORD，经 UTF-8 转换进入 `0x67b3b0` 形成带头部的 CMsg，再入网络发送队列。[E15]
7. 原生网络层使用 TCP/ENet。协议封装函数、队列和网络实现不能被一段裸 XML 替代。

### 离线与确认

- `0x4b9320` 对用户状态值 4 有本机离线记录分支，其他分支继续网络发送；`0x4f49e0` 对尚未解析的原生 user_id 也会创建状态为 4 的记录。因此 IPC 入口返回不表示已联网发送。[E14、E16]
- `string.xml:299` 文案明确：支持离线发送，但发送端在线时对方才能收到。代码与本机保存后续发送的设计一致，未完整验证队列重启恢复。
- 收件端 `0x5be0b0` 发布消息事件后调用 `0x60dca0` 创建命令 1005。[E17]
- `0x6747c0` 生成 X_SEND_MSG_ACK；`0x6748d0` 解析确认；`0x5be1c0 / 0x5bf3d0` 维护待确认状态。[E17]
- `0x676660` 生成 X_SEND_RECEIPT，命令 1006，与网络 ACK 分开。用户回执是否可当作已读，要动态核实触发条件。[E17]

## 3. 原生群聊发送过程

- 同一发送子按钮通过 CQGroupChatLayout 的虚函数槽进入 `0x510740`，再经 0x294 槽进入 `0x50f760`。[E18]
- `0x50f760 → CQGroupMgr::SendMsg @ 0x617600`。
- `0x617600` 检查群 ID、正文和本机成员资格；失败时日志为 “I'm not in qgroup %s”。随后 `0x61b350` 遍历群成员并通过 `0x61b150` 解析非零原生路由标识，逐个调用 `0x6114f0`。[E19]
- `0x6114f0` 形成命令 3011，packer 为 `0x679c10`。[E19、E20]
- `0x679c10` 构造 X_QGROUP_SEND_MSG，明确携带 QGROUP_ID、MSG_ID、MSG、HIDE_RECORD；随后进入同一原生网络封装。[E20]
- 接收侧 `0x679f30 → 0x61af60` 解析群消息并检查群关联信息及本机成员条件，再发布群事件。[上一轮证据]

QGROUP_ID 是逻辑群字符串，既不是群显示名称，也不是 IPMsg 分组。原生群的实现虽然按成员逐个投递，但每份消息保留相同的群语义；这与多次发送 X_SEND_MSG 的联系人群发不同。

未发现独立的群消息全员确认 API。`0x617600` 循环调用投递函数而不汇总每个成员的送达结果；成功返回不能解释为所有成员已收。离线群成员的完整补发机制及是否复用其他确认仍待继续核实。

## 4. 本轮发现的业务发送 IPC

### 静态确认的入口

- 主窗口处理函数 `0x449c60`，不是仅处理 CEF 的 `CSkinDialog::OnCopyData @ 0x522c70`。
- dwData 为 `0x0fecf10f` 的分支，从载荷三个区域读取 UTF-8 字符串；源偏移分别为 0、0x64、0x12c，转换函数 `0x44cbd0` 使用 CP_UTF8。[E22]
- `0x44a20f` 调用 `0x4c41b0`；该函数比较五种选择器：user_name、user_ip、user_id、group_name、group_id。[E23]
- 用户分支最终在 `0x4c44dd` 调用 `0x4b9320`，进入既有原生单聊发送过程。
- 群分支最终在 `0x4c43c9` 调用 `0x4b9c80 → 0x617600`，进入既有原生群聊发送过程。[E23]
- 正文通过 `0x4b8470` 构造客户端自己的消息内容，不要求网关伪造网络身份或手写 X_SEND_MSG。[E24]
- group_id 分支调用 `0x4ee740 → 0x4edfc0` 按群标识查现有群表；user_id 分支调用 `0x4f48d0`，不存在的用户可能被建成本机离线记录。[E16、E25]

### 限制

- 没有找到该入口的公开 SDK/文档，不能称为厂商承诺稳定的 API。
- 已检查的业务分支没有独立登录口令或签名校验；它使用当前客户端状态。Windows 消息访问、会话隔离和完整性级别仍必须动态核实，不得通过提权、注入或修改消息过滤绕过。
- IPC 处理函数没有把消息 ID、网络 ACK 或群成员结果作为结构化响应返回；SendMessage 返回只说明窗口处理结果，不能报告 delivered。
- 载荷三个起始偏移已核实，但完整生产者结构、正文上限和 cbData 契约尚未恢复。不得直接按猜测长度部署，也不进行畸形包或越界测试。
- user_name/group_name 遍历所有匹配对象，可能多目标发送；网关第一版应禁用名称/IP选择，只允许授权白名单中的单个 user_id 或 group_id。
- nwt URI 入口 `0x443ce0 → 0x443e60` 只核实 openuser；不是已证实的带正文发送 CLI。[E26]
- 主窗口还有文件/文件夹导入发送 IPC，不能与上述文本入口混淆。

## 6. 推荐实施设计

第一选择为“独立网关 + 同一用户会话中的 Windows 适配进程 + 官方客户端业务 IPC”。是否实施须先通过下面的单次授权验证。

- 上层只暴露 send_user(user_id, text, request_id) / send_group(group_id, text, request_id)。这是新网关自己的 API，不是声称客户端已有同名 API。
- 仅允许固定白名单里的单个 ID，拒绝名称、多个 ID、空目标、嵌入 NUL；不提供广播和联系人批发入口。
- 绑定目标 EXE 完整路径、版本和 SHA-256；不匹配时停止发送，不能静默退回坐标点击或私有网络伪装。
- 使用正常授权的专用发送账户，正常启动客户端；不覆盖现有用户身份、不读进程内存、不提取凭据。
- 适配进程与客户端处于同一交互用户会话及兼容权限级别；不把目标窗口 IPC 暴露给远程不可信调用方。
- 网关保存请求幂等记录；串行派发。未知结果不自动重发，因为客户端没有提供可验证的幂等/送达回执。
- 状态分开：queued、dispatched_to_client、recipient_observed、failed、unknown。只有独立接收证据才能升级为 recipient_observed。
- UI Automation 用于验证身份、目标群成员、发送后可见记录和接收结果；不是默认的隐藏替代发送路径。
- 如未来需要 Linux 前端，仍保留 Windows 用户会话适配进程；网络入口的认证、授权和部署另行设计，不在本次启用。

## 7. 仅设计、不执行的最小验证

一次验证只发送一次，固定文本 `NWT-GW-AUTH-TEST-0001`，不用自动重试。

推荐首先验证原生群能力：

1. 由操作者准备两个明确授权测试账户 A、B 和仅有这两个成员的原生测试群 G；通过正常客户端确认两者成员资格。不能用生产群或临时群发列表代替。
2. 操作者正常启动、初始化/登录客户端；网关使用 A 的客户端，而不是复制 A 的网络身份。B 保持在线。
3. 只检查同用户会话窗口、版本/哈希、经授权确认的 G 的稳定 group_id，以及 IPC 载荷契约。任何一项不能确认就不发送。
4. 网关仅允许 G 和上述固定文本；将最大尝试次数设为 1。若无法从授权可见信息确认群 ID，应先人工补足信息，不能读取进程内存或解密数据库。
5. 对 A 的客户端发送一次本地请求。不扫描联系人、不调用 IPMsg 广播发现、不向其他用户发送。
6. A 的本地群记录与 B 的原生群窗口各出现一条固定文本，B 显示发送者 A、群 G；不能出现在 B 的单聊窗口或其他会话。
7. 保存请求 ID、客户端版本、时间、A/B 可见结果，不保存凭据。IPC 返回值单独记录，不解释为全员送达。
8. 若超时或结果不明，标记 unknown 并停止；操作者核实后才决定下一次测试。

单聊验证是另一个独立用例：将目标改为白名单 B 的 user_id，其余条件不变。不能在同一次“一条消息”验证里顺带发送单聊和群聊；后续执行需分别授权。

动态待验证：窗口 IPC 是否可达、载荷完整结构/长度与 UTF-8、user_id/group_id 是否准确解析、是否依赖已打开会话、同名对象是否误匹配、客户端离线队列行为、ACK/用户回执可观察性、群成员实际收件范围、UIA 控件可访问性。不开启调试端口，不注入，不修改 UIPI/认证/群权限。
